## 1 引言

### 1.1 编写目的

本文档旨在对"光纤维护服务系统"的软件需求进行完整、准确、规范的描述，作为系统设计、开发、测试和验收的基准文件。本文档的预期读者包括：

- 系统架构师与开发工程师
- 测试工程师
- 项目经理
- 运维人员
- 相关评审人员

### 1.2 项目背景

光纤作为传输系统的核心命脉，其质量直接影响通信的稳定性。本项目旨在开发一套**光纤维护服务系统**，实现对光纤衰耗、中断等关键质量指标的实时监控、查询与智能分析，以提升网络运维效率和故障响应速度。

### 1.3 项目目标

| 编号 | 目标描述                                                     |
| ---- | ------------------------------------------------------------ |
| G-1  | 实现对光纤链路衰耗的实时计算与历史查询                       |
| G-2  | 实现对光纤链路中断及告警状态的实时监控与可视化               |
| G-3  | 支持有源盘与无源盘混合组网场景下的性能与告警数据采集         |
| G-4  | 提供统一 API 网关，支持 Web 端、桌面客户端、移动端等多前端接入 |

### 1.4 术语与缩略语

| 术语/缩略语            | 全称/说明                                                    |
| ---------------------- | ------------------------------------------------------------ |
| 有源盘 (Active Board)  | 具备数据采集能力的功能板卡，可直接获取端口性能值与告警信息，固定 1 个端口 |
| 无源盘 (Passive Board) | 不具备数据采集能力的功能板卡，需通过拓扑寻路获取关联有源盘数据，固定 3 个端口 |
| 源无源盘               | 目标连纤源端的无源盘                                         |
| 宿无源盘               | 目标连纤宿端的无源盘                                         |
| 同层次有源盘           | 与宿端无源盘 Port-3 相连的有源盘（辅助端口，允许空闲）       |
| OOP                    | Output Optical Power，源端口输出光功率                       |
| IOP                    | Input Optical Power，宿端口输入光功率                        |
| Spanloss               | 光纤链路衰耗值                                               |
| 有颜色连纤             | 当前状态为红色或黄色的光纤链路                               |
| 连纤                   | 连接源单盘端口与宿单盘端口之间的光纤链路（端口级粒度，有方向性） |
| 网元 (NE)              | 网络管理的基本单元，一个网元包含若干单盘                     |
| 网元内连纤             | 连纤两端单盘属于同一个网元（src_ne_id == dst_ne_id）         |
| 网元间连纤             | 连纤两端单盘属于不同网元（src_ne_id != dst_ne_id）           |
| gRPC                   | Google Remote Procedure Call，微服务间内部通信协议           |
| API Gateway            | 统一接入层（独立进程），对外提供 REST/WebSocket，对内转发 gRPC |
| Pull Call              | 告警异步拉取任务模式（创建→轮询→取消），用于外部系统批量同步 |
| Server Streaming       | gRPC 服务端流式推送，用于内部事件订阅                        |
| 连纤缓存               | FiberMaintService 本地维护的全量连纤信息缓存                 |
| 告警缓存               | FiberMaintService 本地维护的当前告警信息缓存，存在即激活     |
| 两跳寻路               | 场景2中，从有源盘告警→网元内连纤→无源盘Port-1→网元间连纤的寻路过程 |

## 2 总体描述

### 2.1 产品前景

本系统是一套面向光纤传输网络的运维管理平台，采用微服务架构，通过 C++17 后端服务集群实现光纤链路的全生命周期管理。系统支持多种前端接入方式（Web、桌面客户端、移动端、第三方系统），通过统一 API Gateway 对外提供服务。

### 2.2 产品功能概述

系统核心功能包括：

1. **单盘管理**：有源盘/无源盘的增删查及端口状态管理
2. **拓扑管理**：光纤连纤的创建、删除、查询及拓扑订阅
3. **性能管理**：光功率性能数据的采集、归档、查询
4. **告警管理**：告警的产生、清除、归档、订阅及批量拉取
5. **光纤维护（聚合层）**：光纤性能查询、衰耗计算、颜色状态监控、实时统计与趋势分析

### 2.3 用户角色

| 角色         | 描述                       | 接入方式            |
| ------------ | -------------------------- | ------------------- |
| 运维人员     | 日常监控光纤状态、处理告警 | Web 端 / 桌面客户端 |
| 移动运维人员 | 移动端查看告警与状态       | iOS / Android       |
| 第三方系统   | 通过 OpenAPI 集成          | REST API / API Key  |
| 网络设备     | 主动上报性能与告警数据     | gRPC Push           |

### 2.4 运行环境

| 项目        | 要求                                      |
| ----------- | ----------------------------------------- |
| 后端语言    | C++17                                     |
| RPC 框架    | gRPC + Protocol Buffers 3                 |
| 数据库      | MySQL 8.0 (InnoDB, utf8mb4)，5 个独立实例 |
| API Gateway | C++ (自研) / Envoy（独立进程）            |
| 前端协议    | REST (JSON) + WebSocket                   |
| 内部通信    | gRPC Server-Side Streaming                |

### 2.5 假设与依赖

| 编号 | 描述                                         |
| ---- | -------------------------------------------- |
| A-1  | 设备侧已实现性能数据主动上报（Push）能力     |
| A-2  | 设备侧已实现告警数据直接上报（Push）能力     |
| A-3  | 网络环境支持 gRPC 长连接（Server Streaming） |
| A-4  | 各微服务可独立部署、独立扩缩容               |
| D-1  | 依赖 MySQL 8.0 数据库服务                    |
| D-2  | 依赖 gRPC 运行时环境                         |

## 3 系统架构需求

### 3.1 总体架构

系统采用四层架构设计：

```
┌─────────────────────────────────────────────────────────────────┐
│                        前端接入层                                 │
│  Web端(Vue/React) │ 桌面客户端(Qt/Electron) │ 移动端 │ 第三方系统 │
│                    HTTP/HTTPS + WebSocket                        │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│              API Gateway（统一接入网关，独立进程）                  │
│  REST API │ WebSocket │ 认证鉴权 │ 限流/熔断 │ 协议转换          │
│  端口: 8080(HTTP) / 8443(HTTPS) / 8081(WebSocket)               │
└────────────────────────────┬────────────────────────────────────┘
                             │ gRPC (内部通信)
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                   后端微服务层 (C++17, gRPC)                      │
│  BoardService(:50051) │ TopologyService(:50052)                 │
│  PerformanceService(:50053) │ AlarmService(:50054)              │
│  FiberMaintService(:50055) [聚合层]                              │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                          数据层                                   │
│  db_board(:3307) │ db_topology(:3308) │ db_performance(:3309)   │
│  db_alarm(:3310) │ db_fiber_maint(:3311)                        │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 架构分层说明

| 层次        | 职责                                   | 协议                    | 技术                                |
| ----------- | -------------------------------------- | ----------------------- | ----------------------------------- |
| 前端接入层  | 用户交互、数据展示、实时刷新           | HTTP/HTTPS, WebSocket   | Vue/React, Qt/Electron, iOS/Android |
| API Gateway | 统一入口、协议转换、认证鉴权、限流熔断 | 对外 REST+WS，对内 gRPC | C++ (自研) / Envoy                  |
| 微服务层    | 业务逻辑、数据处理、事件驱动           | gRPC + Server Streaming | C++17, gRPC, Protobuf               |
| 数据层      | 持久化存储、分区管理                   | MySQL Protocol          | MySQL 8.0, InnoDB                   |

## 4 功能需求

### 4.1 核心对象模型

#### 4.1.1 单盘 (Board)

| 类型   | 数据采集能力 | 端口性能   | 端口告警   | 端口数量  |
| ------ | ------------ | ---------- | ---------- | --------- |
| 有源盘 | ✅ 具备       | 可直接获取 | 可直接获取 | 固定 1 个 |
| 无源盘 | ❌ 不具备     | 需拓扑寻路 | 需拓扑寻路 | 固定 3 个 |

**单盘属性：**

| 属性       | 类型                          | 说明                                 |
| ---------- | ----------------------------- | ------------------------------------ |
| board_id   | INT                           | 单盘唯一标识                         |
| board_type | TINYINT (1=ACTIVE, 2=PASSIVE) | 有源盘 / 无源盘                      |
| ne_id      | INT                           | 所属网元标识                         |
| ports[]    | PortInfo[]                    | 端口列表（有源盘 1 个，无源盘 3 个） |

**操作约束：** 单盘仅支持新增和删除操作，不支持修改。

#### 4.1.2 端口 (Port)

| 单盘类型 | 端口   | 固定用途                                             | 是否允许空闲   | 说明                         |
| -------- | ------ | ---------------------------------------------------- | -------------- | ---------------------------- |
| 有源盘   | Port-1 | 网元间连纤（场景1）或网元内连纤（连接无源盘，场景2） | 否             | 唯一端口，一生只关联一条连纤 |
| 无源盘   | Port-1 | 网元间连纤（连接对端网元无源盘）                     | 否             | 场景 2 的目标连纤端口        |
| 无源盘   | Port-2 | 网元内 — 主端口（连接本网元有源盘）                  | 否（不可空闲） | 负责查询性能和告警           |
| 无源盘   | Port-3 | 网元内 — 辅助端口（连接同层次有源盘）                | 是（允许空闲） | 不参与性能/告警核心逻辑      |

**关键约束：**

- 无源盘 Port-2（主端口）不可空闲，若空闲则场景 2 不成立
- 无源盘 Port-3（辅助端口）允许空闲，空闲时颜色判断退化为情况 B
- 有源盘 Port-1 一生只关联一条连纤，不可变更
- 无源盘端口本身不产生告警信息

#### 4.1.3 连纤 (Fiber Connection)

| 属性         | 类型                 | 说明                         |
| ------------ | -------------------- | ---------------------------- |
| fiber_id     | INT (AUTO_INCREMENT) | 连纤唯一标识（系统自动分配） |
| src_board_id | INT                  | 源端单盘                     |
| src_port_id  | TINYINT              | 源端端口编号                 |
| src_ne_id    | INT                  | 源端网元标识                 |
| dst_board_id | INT                  | 宿端单盘                     |
| dst_port_id  | TINYINT              | 宿端端口编号                 |
| dst_ne_id    | INT                  | 宿端网元标识                 |
| created_at   | TIMESTAMP            | 创建时间                     |

**连纤方向性：** 连纤具有明确方向（src → dst），不可反向使用。

**连纤类型判定：**

- `src_ne_id == dst_ne_id` → 网元内连纤
- `src_ne_id != dst_ne_id` → 网元间连纤

#### 4.1.4 告警定义

| 维度     | 取值                                                         |
| -------- | ------------------------------------------------------------ |
| 告警类型 | 产生告警（ALARM_RAISED）、清除告警（ALARM_CLEARED）（仅两种） |
| 告警级别 | 紧急告警（CRITICAL=1）、次要告警（MINOR=2）（仅两种）        |

- 同一端口可同时存在紧急和次要告警（PK 含 alarm_level）
- 无源盘端口本身不产生告警，告警信息仅存在于有源盘端口

#### 4.1.5 场景模型

**场景 1：直连有源盘（网元间连纤）**

```
┌── 网元 NE-A ──┐                    ┌── 网元 NE-B ──┐
│ [有源盘 A]   │    连纤 F001       │  [有源盘 B]   │
│  Port-1 ─────┼────────────────────┼─── Port-1     │
└───────────────┘                    └───────────────┘
```

- 性能：直接获取源端（A/Port-1）OOP 和宿端（B/Port-1）IOP
- 颜色：仅看宿端有源盘 B/Port-1 的告警

**场景 2：经由无源盘连接（网元间连纤）**

```
┌──────── 网元 NE-A ────────┐              ┌──────── 网元 NE-B ────────┐
│ [有源盘 A]   [源无源盘 C] │              │ [宿无源盘 D]   [有源盘 B] │
│  Port-1 ──── Port-2(主)   │              │  Port-3(辅)── Port-1      │
│             Port-3(辅)    │              │  Port-2(主)               │
│             Port-1(网元间)─┼──────────────┼── Port-1(网元间)         │
└──────────────────────────┘              └────────────────────────────┘
```

- 性能：源端 C.Port-2→有源盘A→OOP；宿端 D.Port-2→有源盘B→IOP
- 颜色（仅宿端）：
  - 宿端 D.Port-2→有源盘B→告警
  - 宿端 D.Port-3：空闲→情况B / 连接有源盘A2→情况A

### 4.2 性能管理模块

| 编号  | 功能         | 需求描述                                                     | 优先级 |
| ----- | ------------ | ------------------------------------------------------------ | ------ |
| PM-01 | 性能上报     | 设备主动上报（Push），调用 PerformanceService.ReportPerformance RPC 写入 | 高     |
| PM-02 | 性能归档     | 每 15min 扫描 current_performance → INSERT history_performance → DELETE current（清空） | 高     |
| PM-03 | 当前性能查询 | 提供端口级别的当前性能值查询接口                             | 高     |
| PM-04 | 历史性能查询 | 提供基于端口 + 时间段的历史性能值查询接口                    | 高     |
| PM-05 | 批量性能查询 | 支持按端口列表批量查询当前/历史性能（上限 ≤200）             | 中     |
| PM-06 | 数据保留策略 | 历史性能数据按自然月保留 1 个月                              | 中     |

**PM-02 性能归档详细流程：**

```
[每 15 分钟定时任务]
  → SELECT * FROM current_performance
  → INSERT INTO history_performance (board_id, port_id, recorded_at, oop_value, iop_value)
    VALUES (...)  -- recorded_at = 当前时间
  → DELETE FROM current_performance
  → [等待下次设备上报写入新数据]
```

> ⚠️ 归档后 current_performance 表被清空，直到设备下次上报。若设备在 15min 内未上报，则查询返回 NULL。

### 4.3 告警管理模块

| 编号  | 功能                      | 需求描述                                              | 优先级 |
| ----- | ------------------------- | ----------------------------------------------------- | ------ |
| AL-01 | 告警上报                  | 设备直接上报，调用 AlarmService.ReportAlarm RPC 写入  | 高     |

### 4.7 颜色重算机制（核心功能）

#### 4.7.1 设计原则

| 原则           | 说明                                                         |
| -------------- | ------------------------------------------------------------ |
| 仅宿端判定     | 颜色仅通过宿端判断，源端 Port-3 完全不参与                   |
| 仅网元间连纤   | 颜色仅针对网元间连纤（src_ne_id ≠ dst_ne_id）                |
| 缓存驱动       | 颜色判定通过本地告警缓存 + 连纤缓存完成，不实时调用外部 RPC  |
| 两类触发       | 告警消息触发 + 连纤消息触发                                  |
| 不订阅 Board   | FiberMaintService 不订阅 BoardEvents                         |
| 告警缓存唯一性 | 同一端口(board_id+port_id)同一告警类型(alarm_level)只存一条记录 |
| 存在即激活     | 告警缓存中存在该记录 → 该端口当前存在该级别告警；不存在 → 无该级别告警 |

#### 4.7.2 触发源总览

| 类别     | 触发事件                   | 来源                     | 影响                                  |
| -------- | -------------------------- | ------------------------ | ------------------------------------- |
| 告警消息 | ALARM_RAISED               | AlarmService → Stream    | 写入告警缓存 → 重算关联网元间连纤颜色 |
| 告警消息 | ALARM_CLEARED              | AlarmService → Stream    | 删除告警缓存 → 重算关联网元间连纤颜色 |
| 连纤消息 | FIBER_CREATED (网元间)     | TopologyService → Stream | 初始化新连纤颜色                      |
| 连纤消息 | FIBER_DELETED (网元间)     | TopologyService → Stream | 从缓存/统计中移除                     |
| 连纤消息 | FIBER_CREATED (网元内)     | TopologyService → Stream | 场景变更 → 重算关联网元间连纤         |
| 连纤消息 | FIBER_DELETED (网元内)     | TopologyService → Stream | 场景变更 → 重算关联网元间连纤         |
| 启动同步 | Pull Call + BatchGetFibers | 自身                     | 全量初始化                            |

#### 4.7.3 本地缓存设计

**连纤缓存（方案C）：**

FiberMaintService 在本地维护全量连纤信息缓存，解决 FIBER_DELETED 事件携带信息不足的问题。

| 时机          | 操作     | 说明                                                         |
| ------------- | -------- | ------------------------------------------------------------ |
| 服务启动      | 全量加载 | TopologyService.BatchGetFibers 获取所有连纤，写入缓存        |
| FIBER_CREATED | INSERT   | 收到事件后调用 GetFiber 获取完整信息，写入缓存               |
| FIBER_DELETED | 先读后删 | 收到事件后从缓存读取完整信息（此时DB已删除），处理完后从缓存移除 |
| 断线重连      | 全量刷新 | 重新拉取全量连纤，重建缓存                                   |

**告警缓存：**

| 原则           | 说明                                                         |
| -------------- | ------------------------------------------------------------ |
| 唯一性         | 同一端口（board_id + port_id）同一告警类型（alarm_level）只存一条记录 |
| 存在即激活     | 缓存中存在该记录 → 表示该端口当前存在该级别告警              |
| 不存在即无告警 | 缓存中不存在该记录 → 表示该端口当前无该级别告警              |
| 与DB对齐       | 与 current_alarms 表 PK(board_id, port_id, alarm_level) 一一对应 |

| 操作           | 触发                | 行为                                                         |
| -------------- | ------------------- | ------------------------------------------------------------ |
| 写入（INSERT） | ALARM_RAISED        | alarm_cache_[{board_id, port_id, alarm_level}] = {raised_at} |
| 删除（DELETE） | ALARM_CLEARED       | alarm_cache_.erase({board_id, port_id, alarm_level})         |
| 全量加载       | 服务启动 / 断线重连 | Pull Call → 清空 → 逐条写入                                  |
| 查询（EXISTS） | 颜色计算            | alarm_cache_.count({board_id, port_id, alarm_level}) > 0     |

#### 4.7.4 告警消息触发颜色重算

**统一处理流程：**

```
AlarmEvent {event_type, board_id, port_id, alarm_level, timestamp}
   ├─ Step 1: 更新告警缓存
   ├─ Step 2: 两跳寻路，找到受影响的网元间连纤
   ├─ Step 3: 判断告警端口在网元间连纤中的角色（仅宿端影响颜色）
   ├─ Step 4: 判定场景类型（场景1/场景2情况A/B/C）
   ├─ Step 5: 从告警缓存读取宿端相关端口告警
   ├─ Step 6: 按颜色规则计算新颜色
   └─ Step 7: 比较新旧颜色 → 变化则更新并推送
```

**两跳寻路规则：**

| 第一跳结果                      | 对端端口 | 处理                                    |
| ------------------------------- | -------- | --------------------------------------- |
| 网元间连纤，本端口是 dst        | —        | 场景1，宿端告警，重算                   |
| 网元间连纤，本端口是 src        | —        | 源端告警，**跳过**                      |
| 网元内连纤，对端是无源盘 Port-2 | Port-2   | 第二跳→Port-1→网元间连纤，判断宿端/源端 |
| 网元内连纤，对端是无源盘 Port-3 | Port-3   | 第二跳→Port-1→网元间连纤，判断宿端/源端 |
| 网元内连纤，对端是有源盘        | —        | 跳过                                    |
| 无关联连纤                      | —        | 跳过                                    |

#### 4.7.5 连纤消息触发颜色重算

**场景变更矩阵：**

| 操作 | 连纤类型          | 影响端口                   | 场景变更 | 颜色影响               |
| ---- | ----------------- | -------------------------- | -------- | ---------------------- |
| 创建 | 网元内（↔Port-2） | 宿无源盘 Port-2: 空闲→占用 | C → A/B  | 可能 绿→红/黄          |
| 创建 | 网元内（↔Port-3） | 宿无源盘 Port-3: 空闲→占用 | B → A    | 判定逻辑变更           |
| 删除 | 网元内（↔Port-2） | 宿无源盘 Port-2: 占用→空闲 | A/B → C  | 强制变绿               |
| 删除 | 网元内（↔Port-3） | 宿无源盘 Port-3: 占用→空闲 | A → B    | 判定逻辑变更           |
| 创建 | 网元间            | 新连纤                     | 新增     | 初始化（基于告警缓存） |
| 删除 | 网元间            | 被删连纤                   | 移除     | 从统计移除             |

> Port-1 无网元间连纤时，Port-2/Port-3 变更直接跳过；之后 Port-1 创建网元间连纤时，FIBER_CREATED(网元间) 触发重新计算颜色。

#### 4.7.7 并发颜色重算 — 锁机制（待进一步设计）

**问题场景：**

| 场景                                 | 风险                     |
| ------------------------------------ | ------------------------ |
| 同一连纤同时收到两个告警事件         | 两次重算结果可能互相覆盖 |
| 告警事件 + 连纤删除同时发生          | 正在重算时连纤被删除     |
| 同一无源盘 Port-2 和 Port-3 同时变更 | 两次场景变更交叉执行     |

**设计方向（待细化）：**

| 方案     | 说明                                         |
| -------- | -------------------------------------------- |
| 串行队列 | 按 fiber_id 分桶，同一连纤的重算请求串行执行 |
| 读写锁   | alarm_cache_ / fiber_colors 表/缓存加读写锁  |
| 版本号   | 每次重算携带版本号，写入时 CAS 校验          |
| 最终一致 | 允许短暂不一致，后到事件覆盖先到结果         |

### 4.8 断线重连与增量补偿机制

#### 4.8.1 内部 gRPC Stream 断线重连

| 订阅方            | 订阅源                               | 断线检测                | 重连策略                     | 补偿机制                                                |
| ----------------- | ------------------------------------ | ----------------------- | ---------------------------- | ------------------------------------------------------- |
| FiberMaintService | AlarmService.SubscribeAlarmEvents    | 心跳超时 / stream error | 指数退避（1s→2s→4s→...→60s） | Pull Call → 清空 alarm_cache_ → 全量重建 → 全量重算颜色 |
| FiberMaintService | TopologyService.SubscribeFiberEvents | 心跳超时 / stream error | 指数退避                     | BatchGetFibers → 重建连纤缓存 → 全量重算                |
| TopologyService   | BoardService.SubscribeBoardEvents    | 心跳超时 / stream error | 指数退避                     | BatchGetBoards 刷新缓存                                 |
| API Gateway       | 各服务 Stream                        | 心跳超时 / stream error | 指数退避                     | 无需补偿（仅转发增量）                                  |

#### 4.8.2 前端 WebSocket 断线重连

| 步骤        | 说明                                                       |
| ----------- | ---------------------------------------------------------- |
| 1. 检测断线 | 客户端心跳超时（30s 无 pong）                              |
| 2. 自动重连 | 指数退避重连（1s, 2s, 4s, ... 最大 60s）                   |
| 3. 全量拉取 | 重连成功后，重新拉取当前全量状态（有颜色连纤、告警、统计） |
| 4. 恢复订阅 | 重新发送 subscribe 消息，接收增量事件                      |
