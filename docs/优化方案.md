## 一、背景与问题

### 1.1 业务背景

FiberMaintService 负责根据网元端口告警状态，实时计算网元间连纤（Fiber）的健康颜色（GREEN / YELLOW / RED），并通过 WebSocket 推送给前端展示，同时持久化到数据库。

当前颜色计算规则：

| 场景                           | 条件                      | 颜色             |
| ------------------------------ | ------------------------- | ---------------- |
| 场景1（宿端有源盘）            | 无告警                    | GREEN            |
| 场景1                          | 仅MINOR告警               | YELLOW           |
| 场景1                          | 有CRITICAL告警            | RED              |
| 场景2A（Port-2 B + Port-3 A2） | 双方均无告警              | GREEN            |
| 场景2A                         | 任一方有MINOR             | YELLOW           |
| 场景2A                         | 单侧CRITICAL + 对侧无告警 | GREEN（R-23）    |
| 场景2A                         | 双方均有CRITICAL          | RED              |
| 场景2B（仅Port-2 B）           | 同场景1规则               | GREEN/YELLOW/RED |
| 场景2C（无有源盘）             | 永远                      | GREEN            |

### 1.2 当前实现的问题

#### 问题一：性能瓶颈——同步阻塞

```
当前处理链路（每条告警）：
  ① 更新 alarm_cache_（加锁）           ~0.01ms
  ② 两跳寻路找受影响连纤（遍历）         ~0.05ms
  ③ 全量读取缓存 + 颜色计算             ~0.02ms
  ④ 颜色比较                            ~0.001ms
  ⑤ DB写入（同步阻塞）                  ~2-5ms  ← 瓶颈
  ⑥ WebSocket推送（同步）               ~0.5ms
  ─────────────────────────────────
  总计：~3-6ms/条
  理论吞吐：~160-330条/秒
```

**告警风暴（5000~20000条/秒）下严重不足。**

#### 问题二：并发安全——锁竞争严重

当前使用 Per-Port Lane + 光纤级互斥锁 + 全局序列号校验 + 一致性快照 + 拓扑版本号 + COW快照，共6种以上同步机制，复杂度高且仍有竞态风险。

#### 问题三：无效计算——缺乏过滤

- 每条告警都触发完整颜色计算，即使结果不变
- 闪断告警（RAISED/CLEARED快速交替）产生大量无效计算
- 无短路预判机制

#### 问题四：场景耦合——扩展性差

- 场景知识硬编码在结构体字段、枚举、if/else分支中
- 新增场景需修改6+个位置
- 违反开闭原则

#### 问题五：队列溢出——无背压保护

- 告警风暴下接收队列无界增长 → OOM风险
- 无降级策略
- 无闪断抑制

### 1.3 关键约束

| 约束             | 说明                                             |
| ---------------- | ------------------------------------------------ |
| 告警串行上报     | AlarmEvent 通过单条 gRPC Stream 全局有序到达     |
| 优化范围         | 仅限 FiberMaintService 内部，不改动 AlarmService |
| 业务规则不可违反 | R-19、R-23、R-25、方案C（先读后删）              |
| 颜色未变不通知   | 比较后相同则丢弃                                 |

## 二、设计目标

| 指标                       | 目标值              | 当前值              |
| -------------------------- | ------------------- | ------------------- |
| 正常告警端到端延迟         | < 50ms              | 3~6ms（但含同步DB） |
| 告警风暴吞吐（20000条/秒） | 不丢失CRITICAL      | 积压/溢出           |
| 闪断告警无效计算过滤率     | > 90%               | 0%                  |
| 接收队列                   | 有界 + 背压，不溢出 | 无界/无保护         |
| 场景2多端口一致性          | 结构性保证          | 依赖锁              |
| 新增场景改动量             | 1个文件 + 1行注册   | 6+个文件            |
| 锁使用                     | 无锁（单写者模型）  | 6+种锁              |

## 三、解决方案总览

### 3.1 核心设计思想

```
一个原则：串行输入是最强的有序性保证，不引入并发来"加速"

两个解耦：
  - 消费与计算解耦（dirty标记 vs 立即计算）
  - 计算与输出解耦（change_queue vs 同步DB）

三个消除：
  - 消除锁（单写者模型）
  - 消除两跳寻路（预建依赖图）
  - 消除无效计算（短路预判 + 闪断抑制）

四个保证：
  - 同端口时序（串行天然保证）
  - 场景2一致性（聚合窗口 + 单线程）
  - 拓扑-告警无交叉（同一线程顺序处理）
  - 不丢CRITICAL（背压策略中CRITICAL永不丢弃）
```

### 3.3 线程模型

| 线程                 | 职责                               | 数量 | 锁                      |
| -------------------- | ---------------------------------- | ---- | ----------------------- |
| gRPC Stream 读取线程 | 从Stream读取事件，写入recv_buffer_ | 1    | 无（SPSC环形缓冲）      |
| Layer 1 消费线程     | 串行处理所有事件，更新状态         | 1    | **无**（单写者）        |
| Layer 2 计算线程     | 定期批量计算颜色                   | 1    | 无（dirty_set原子交换） |
| Layer 3 输出线程     | 批量DB写入 + WS推送                | 1    | 无（change_queue SPSC） |
| 慢路径线程           | 日志、指标、非关键IO               | 1    | 无（slow_queue SPSC）   |
| 风暴控制线程         | 速率统计、降级切换                 | 1    | 无（读原子变量）        |

**总计：6个线程，无任何mutex。**

## 四、详细设计

### 4.1 核心数据结构

#### 4.1.1 通用颜色上下文（动态状态向量）

```
ColorContext {
    int32_t fiber_id;              // 连纤ID
    int32_t scenario_id;           // 关联的场景ID
    
    vector<uint16_t> alarm_counts; // 动态告警状态向量
                                   // 索引由场景Schema定义
                                   // 场景1: [dst_crit, dst_minor]
                                   // 场景2A: [b_crit, b_minor, a2_crit, a2_minor]
    
    FiberColor current_color;      // 当前颜色（权威值）
    bool is_dirty;                 // 是否需要重算
    int64_t dirty_since_ms;        // 标记dirty的时间戳
    bool has_pending_change;       // 闪断抑制期间的待处理标记
}
```

#### 4.1.2 端口→连纤依赖图

```
port_dependency_map_:
    unordered_map<PortKey, vector<SlotBinding>>

PortKey {
    int32_t board_id;
    int32_t port_id;
}

SlotBinding {
    int32_t fiber_id;       // 受影响的网元间连纤
    int32_t slot_index;     // 更新 ColorContext.alarm_counts 的哪个slot
    int8_t  alarm_level;    // 哪个级别的告警（CRITICAL/MINOR）
}
```

#### 4.1.3 告警缓存

```
alarm_cache_:
    unordered_map<AlarmCacheKey, AlarmCacheEntry>

AlarmCacheKey {
    int32_t board_id;
    int32_t port_id;
    int8_t  alarm_level;
}

AlarmCacheEntry {
    int64_t raised_at_ms;
    int64_t sequence_no;    // 幂等用
}
```

#### 4.1.4 连纤缓存

```
fiber_cache_:
    unordered_map<int32_t, FiberInfo>

FiberInfo {
    int32_t fiber_id;
    int32_t src_ne_id, src_board_id, src_port_id;
    int32_t dst_ne_id, dst_board_id, dst_port_id;
    bool is_inter_ne;
    bool dst_is_active;
    int32_t port2_board_id;
    int32_t port3_board_id;
}
```

#### 4.1.5 闪断检测器

```
flap_detectors_:
    unordered_map<AlarmCacheKey, FlapState>

FlapState {
    uint16_t flap_count;
    int64_t  window_start_ms;
    int64_t  last_event_ms;
    int8_t   last_event_type;
    bool     suppressed;
}
```

### 4.2 Layer 0：有界接收缓冲 + 背压控制

#### 4.2.1 设计

```
recv_buffer_: SPSC 环形缓冲区
容量：50000 条事件
写入者：gRPC Stream 读取线程
消费者：Layer 1 串行消费线程
```

#### 4.2.2 背压策略

| 水位 | 条件       | 行为                                           |
| ---- | ---------- | ---------------------------------------------- |
| 正常 | 占用 < 60% | 正常消费                                       |
| 警告 | 60% ~ 80%  | WARN日志，跳过慢路径                           |
| 高压 | 80% ~ 95%  | 丢弃MINOR告警，仅保留CRITICAL + 连纤事件       |
| 溢出 | > 95%      | 覆盖最旧事件 + 记录丢弃计数 + 标记"需全量重算" |

#### 4.2.3 关键约束

- **连纤事件（FIBER_CREATED/DELETED）永不丢弃**
- **CRITICAL告警永不丢弃**
- 丢弃的MINOR通过风暴后全量重算补偿

#### 4.2.4 流程图

```
┌──────────────────┐
│ gRPC Stream 读取  │
└────────┬─────────┘
         │ event
         ▼
┌──────────────────┐     满      ┌─────────────────────┐
│ try_push(event)  │────────────▶│ 背压策略判定         │
└────────┬─────────┘             └──────────┬──────────┘
         │ 成功                             │
         ▼                                  ▼
┌──────────────────┐             ┌─────────────────────┐
│ Layer 1 消费     │             │ < 80%: sleep(1ms)   │
└──────────────────┘             │   重试push          │
                                 │ 80~95%: 丢弃MINOR  │
                                 │ > 95%: 覆盖最旧    │
                                 └─────────────────────┘
```

### 4.3 Layer 1：串行消费引擎

#### 4.3.1 设计原则

- **单线程**：所有事件顺序处理，天然有序，无任何锁
- **极快路径**：每条事件处理 < 0.01ms，不做任何IO
- **慢路径分离**：日志、指标通过异步队列交给独立线程

**通用规则（所有场景共享）：**

| S2A-1 | 场景2A | RAISED CRITICAL + 对侧无任何告警          | R-23单侧紧急=绿，跳过 |
| S2A-2 | 场景2A | RED + CLEARED CRITICAL + 对侧仍有CRITICAL | 双方紧急仍RED，跳过   |

### 4.4 Layer 2：延迟批量颜色计算

#### 4.4.1 触发机制

```
Layer2 Loop:
    while (running):
        wait_for_notification(timeout = aggregate_window_ms)
        sleep(aggregate_window_ms)          // 聚合窗口
        fibers = dirty_set_.steal_all()     // 原子交换为空集
        for batch in chunk(fibers, 500):
            for fiber_id in batch:
                calculate_fiber_color(fiber_id)
            yield()                         // 批间让出CPU
```

| 模式 | 条件              | 窗口  | 说明     |
| ---- | ----------------- | ----- | -------- |
| 正常 | dirty_set < 100   | 10ms  | 低延迟   |
| 高压 | dirty_set 100~500 | 30ms  | 适度合并 |
| 风暴 | dirty_set > 500   | 100ms | 大量合并 |
| 极端 | dirty_set > 2000  | 200ms | 最大合并 |

#### 4.4.4 场景2多端口一致性保证

```
串行模型下的自然保证（无需锁）：

t=0ms   B的CRITICAL到达 → Layer1: alarm_counts[0]=1, dirty += fiber_200
t=3ms   A2的CRITICAL到达 → Layer1: alarm_counts[2]=1, dirty += fiber_200（幂等）
t=10ms  聚合窗口到期 → Layer2: 取出fiber_200
        → alarm_counts = [1, 0, 1, 0]
        → evaluate_color → kCaseATable[2][2] = RED ✓

关键：Layer1单线程，B和A2的更新必然在Layer2计算之前完成。
聚合窗口确保"逻辑上同时"的告警在一次计算中被看到。
```

### 4.5 Layer 3：异步批量输出

#### 4.5.1 处理流程

```
Layer3 Loop:
    while (running):
        batch = change_queue_.pop_batch(max=100, timeout=50ms)
        if (batch.empty()): continue
        
        deduped = deduplicate_by_fiber(batch)
        
        color_changes = filter(deduped, type == COLOR_CHANGE)
        fiber_deletes = filter(deduped, type == FIBER_COLOR_DELETE)
        
        if (!color_changes.empty()):
            db_batch_upsert_colors(color_changes)
            db_batch_insert_history(color_changes)
        
        if (!fiber_deletes.empty()):
            db_batch_delete_colors(fiber_deletes)
        
        ws_push_with_rate_limit(deduped)
```

#### 4.5.2 同fiber去重

```
50ms窗口内同一fiber可能多次变色：
  GREEN → YELLOW → RED（B先MINOR后CRITICAL）

去重后只保留：GREEN → RED
  → DB只写一次最终状态
  → WebSocket只推一次最终结果
  → 若 old == new（变了又变回来）→ 完全丢弃
```

#### 4.5.3 WebSocket限流

| 变更数量 | 推送方式                                   |
| -------- | ------------------------------------------ |
| ≤ 50条   | 逐条推送                                   |
| > 50条   | 合并为 `BATCH_FIBER_COLOR_CHANGE` 批量消息 |
| 速率上限 | 200条/秒，超限延迟到下一批次               |

### 4.7 风暴控制器

#### 4.7.1 三级降级

| 级别 | 进入条件            | Layer 1                 | Layer 2            | Layer 3              |
| ---- | ------------------- | ----------------------- | ------------------ | -------------------- |
| 正常 | < 100条/秒          | 全量处理                | 窗口10ms           | 正常批量             |

#### 4.7.2 退出与恢复

```
退出条件：连续10秒 < 100条/秒

恢复动作：
  ① 触发全量重算（所有fiber标记dirty）
  ② 补写历史记录（风暴期间跳过的）
  ③ 恢复所有配置到正常值
```

| Layer 2 | 查表 + 比较（每fiber）          | ~0.005ms | ~200,000次/秒 |
| Layer 3 | 批量DB写入（100条/批）          | ~5ms/批  | ~20,000条/秒  |

### 9.2 端到端延迟

| 场景                  | 延迟      | 说明                       |
| --------------------- | --------- | -------------------------- |
| 正常告警→颜色变化推送 | 10~60ms   | 聚合窗口 + 计算 + 输出窗口 |
| 正常告警→无变化丢弃   | 10ms      | 聚合窗口后短路/比较        |
| 场景2多端口           | 10~60ms   | 自然合并                   |
| 告警风暴              | 100~200ms | 风暴模式聚合窗口           |

### 9.3 对比

| 指标         | 优化前          | 优化后                  | 提升     |
| ------------ | --------------- | ----------------------- | -------- |
| 单条处理延迟 | 3-6ms（含DB）   | 0.01ms（Layer1）        | 300x     |

| 颜色计算次数 | 每条告警一次    | 每dirty fiber每窗口一次 | 减少90%+ |
| DB写入次数   | 每次变化一次    | 批量去重后              | 减少80%+ |
| 锁竞争       | 6+种锁          | 无锁                    | 消除     |

### 9.4 极端场景验证

```
20000条/秒风暴持续10秒：
  预聚合后（AlarmService侧，若启用）：~2000条/秒
  无预聚合：20000条/秒
  
  Layer 1消费：0.01ms × 20000 = 200ms/秒 → CPU占用20% → 无积压 ✓
  dirty_set峰值：~500个fiber → 内存 < 100KB → 无溢出 ✓
  Layer 2：每100ms计算500个fiber → 2.5ms → 无积压 ✓
  Layer 3：100ms内去重后~200条变更 → 批量写入 → 无积压 ✓
  recv_buffer：20000×0.01ms消费 vs 20000到达 → 水位稳定 ✓

结论：即使极端风暴，各层均有余量，不会溢出。
```

## 十一、风险与缓解

| 风险                 | 影响                 | 缓解措施                    |
| -------------------- | -------------------- | --------------------------- |
| 聚合窗口引入延迟     | 颜色更新延迟10~200ms | 前端可接受；风暴外仅10ms    |
| 闪断抑制期间颜色不准 | 抑制期间不更新       | 2秒后自动恢复；最终状态正确 |
| 风暴期间丢弃MINOR    | MINOR告警丢失        | 风暴后全量重算补偿          |
| DB故障               | 颜色未持久化         | 本地WAL + 恢复后回放        |
| Stream断连           | 告警中断             | 重连 + 全量同步             |
| 计数下溢             | 颜色计算错误         | 防御性检查 + 触发全量重算   |

## 十二、总结

本方案通过**串行消费 + 流水线解耦 + 延迟聚合 + 场景插件化**四个核心设计，在保持业务正确性的前提下，实现了：

1. **性能**：吞吐从200条/秒提升到80000条/秒，满足极端告警风暴
2. **正确性**：串行模型 + 聚合窗口结构性保证场景2一致性，无需任何锁
3. **稳定性**：有界缓冲 + 背压 + 三级降级 + 闪断抑制，队列不溢出
4. **扩展性**：新增场景仅需实现接口 + 注册，引擎层零改动
5. **简洁性**：6个线程、无锁、无复杂同步机制，可维护性大幅提升
