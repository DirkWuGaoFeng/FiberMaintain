# 光纤维护服务系统 — 需求规格说明书（完善版 v14.4）

---

## 1. 引言

### 1.1 项目背景

光纤作为传输系统的核心命脉，其质量直接影响通信的稳定性。本项目旨在开发一套光纤维护服务系统，实现对光纤衰耗、中断等关键质量指标的实时监控、查询与智能分析，以提升网络运维效率和故障响应速度。

### 1.2 项目目标

| 编号 | 目标                                                           |
| ---- | -------------------------------------------------------------- |
| G-1  | 实现对光纤链路衰耗的实时计算与历史查询                         |
| G-2  | 实现对光纤链路中断及告警状态的实时监控与可视化                 |
| G-3  | 支持有源盘与无源盘混合组网场景下的性能与告警数据采集           |
| G-4  | 提供统一 API 网关，支持 Web 端、桌面客户端、移动端等多前端接入 |

### 1.3 术语与缩略语

| 术语                   | 说明                                                                          |
| ---------------------- | ----------------------------------------------------------------------------- |
| 有源盘 (Active Board)  | 具备数据采集能力的功能板卡，可直接获取端口性能值与告警信息，固定 1 个端口     |
| 无源盘 (Passive Board) | 不具备数据采集能力的功能板卡，需通过拓扑寻路获取关联有源盘数据，固定 3 个端口 |
| 源无源盘               | 目标连纤源端的无源盘                                                          |
| 宿无源盘               | 目标连纤宿端的无源盘                                                          |
| 同层次有源盘           | 与宿端无源盘 Port-3 相连的有源盘（辅助端口，允许空闲）                        |
| OOP                    | Output Optical Power，源端口输出光功率                                        |
| IOP                    | Input Optical Power，宿端口输入光功率                                         |
| Spanloss               | 光纤链路衰耗值                                                                |
| 有颜色连纤             | 当前状态为红色或黄色的光纤链路                                                |
| 连纤                   | 连接源单盘端口与宿单盘端口之间的光纤链路（端口级粒度，有方向性）              |
| 网元 (NE)              | 网络管理的基本单元，一个网元包含若干单盘                                      |
| 网元内连纤             | 连纤两端单盘属于同一个网元（src_ne_id == dst_ne_id）                          |
| 网元间连纤             | 连纤两端单盘属于不同网元（src_ne_id != dst_ne_id）                            |
| gRPC                   | Google Remote Procedure Call，微服务间内部通信协议                            |
| API Gateway            | 统一接入层（独立进程），对外提供 REST/WebSocket，对内转发 gRPC                |
| Pull Call              | 告警异步拉取任务模式（创建→轮询→取消），用于外部系统批量同步                |
| Server Streaming       | gRPC 服务端流式推送，用于内部事件订阅                                         |
| 连纤缓存               | FiberMaintService 本地维护的全量连纤信息缓存（方案C）                         |
| 告警缓存               | FiberMaintService 本地维护的当前告警信息缓存，存在即激活                      |
| 两跳寻路               | 场景2中，从有源盘告警→网元内连纤→无源盘Port-1→网元间连纤的寻路过程         |

| 步骤        | 说明                                                                 |
| ----------- | -------------------------------------------------------------------- |
| 1. 检测断线 | 客户端心跳超时（30s 无 pong）                                        |

## 3. 核心对象与场景模型

### 3.1 核心对象定义

#### 3.1.1 单盘 (Board)

| 类型   | 数据采集能力 | 端口性能   | 端口告警   | 端口数量  |
| ------ | ------------ | ---------- | ---------- | --------- |
| 有源盘 | ✅ 具备      | 可直接获取 | 可直接获取 | 固定 1 个 |
| 无源盘 | ❌ 不具备    | 需拓扑寻路 | 需拓扑寻路 | 固定 3 个 |

单盘属性：

| 属性       | 类型                          | 说明                                 |
| ---------- | ----------------------------- | ------------------------------------ |
| board_id   | INT                           | 单盘唯一标识                         |
| board_type | TINYINT (1=ACTIVE, 2=PASSIVE) | 有源盘 / 无源盘                      |
| ne_id      | INT                           | 所属网元标识                         |
| ports[]    | PortInfo[]                    | 端口列表（有源盘 1 个，无源盘 3 个） |

单盘操作约束：单盘仅支持新增和删除操作，不支持修改。

#### 3.1.2 端口 (Port)

端口设计（方案 A：固定映射）：

| 单盘类型 | 端口   | 固定用途                                              | 是否允许空闲   | 说明                                      |
| -------- | ------ | ----------------------------------------------------- | -------------- | ----------------------------------------- |
| 有源盘   | Port-1 | 网元间连纤（场景1）或 网元内连纤（连接无源盘，场景2） | 否             | 唯一端口，一生只关联一条连纤              |
| 无源盘   | Port-1 | 网元间连纤（连接对端网元无源盘）                      | 否             | 场景 2 的目标连纤端口                     |
| 无源盘   | Port-2 | 网元内 — 主端口（连接本网元有源盘）                  | 否（不可空闲） | 负责查询性能和告警；若空闲则场景 2 不成立 |
| 无源盘   | Port-3 | 网元内 — 辅助端口（连接同层次有源盘）                | 是（允许空闲） | 不参与性能/告警核心逻辑                   |

⚠️ 关键约束：

- 无源盘 Port-2（主端口）不可空闲。若空闲，场景 2 不成立。
- 无源盘 Port-3（辅助端口）允许空闲。空闲时颜色判断退化为情况 B。
- 有源盘 Port-1 一生只关联一条连纤（网元间或网元内，二选一），不可变更。
- 无源盘端口本身不产生告警信息，告警只能通过其连接的有源盘端口获取。

#### 3.1.3 连纤 (Fiber Connection)

| 属性         | 类型                 | 说明                         |
| ------------ | -------------------- | ---------------------------- |
| fiber_id     | INT (AUTO_INCREMENT) | 连纤唯一标识（系统自动分配） |
| src_board_id | INT                  | 源端单盘                     |
| src_port_id  | TINYINT              | 源端端口编号                 |
| src_ne_id    | INT                  | 源端网元标识                 |
| dst_board_id | INT                  | 宿端单盘                     |
| dst_port_id  | TINYINT              | 宿端端口编号                 |
| dst_ne_id    | INT                  | 宿端网元标识                 |
| created_at   | TIMESTAMP            | 创建时间                     |

连纤方向性：连纤具有明确方向（src → dst），不可反向使用。

连纤类型判定：

- `src_ne_id == dst_ne_id` → 网元内连纤
- `src_ne_id != dst_ne_id` → 网元间连纤

#### 3.1.4 告警定义

| 维度     | 取值                                                          |
| -------- | ------------------------------------------------------------- |
| 告警类型 | 产生告警（ALARM_RAISED）、清除告警（ALARM_CLEARED）（仅两种） |
| 告警级别 | 紧急告警（CRITICAL=1）、次要告警（MINOR=2）（仅两种）         |

- 同一端口可同时存在不同的告警级别（PK 含 alarm_level）。
- 无源盘端口本身不产生告警，告警信息仅存在于有源盘端口。

#### 3.1.5 "同层次有源盘"定义

与宿端无源盘 Port-3（辅助端口）相连的有源盘。

> 颜色判断**仅基于宿端**。源端无源盘 C 的 Port-3 **完全不参与**颜色计算。

### 3.2 场景模型

**场景 1：直连有源盘（网元间连纤）**

```
┌── 网元 NE-A ──┐                    ┌── 网元 NE-B ──┐
│ [有源盘 A]   │    连纤 F001       │  [有源盘 B]   │
│  ne_id=100   │    (网元间)        │   ne_id=200   │
│  Port-1 ─────┼────────────────────┼─── Port-1     │
└───────────────┘                    └───────────────┘
```

- 性能：直接获取源端（A/Port-1）OOP 和宿端（B/Port-1）IOP
- 颜色：**仅看宿端**有源盘 B/Port-1 的告警

**场景 2：经由无源盘连接（网元间连纤）**

```
┌──────── 网元 NE-A ────────┐              ┌──────── 网元 NE-B ────────┐
│ [有源盘 A]   [源无源盘 C] │              │ [宿无源盘 D]   [有源盘 B] │
│ ne_id=100    ne_id=100    │              │ ne_id=200     ne_id=200   │
│  Port-1 ──── Port-2(主)   │              │  Port-3(辅)── Port-1      │
│             Port-3(辅)    │              │  Port-2(主)               │
│             Port-1(网元间)─┼──────────────┼── Port-1(网元间)         │
│                          │   连纤 F001  │                            │
│  网元内连纤:             │              │  网元内连纤:               │
│  A.Port-1 ←→ C.Port-2   │              │  D.Port-2 ←→ B.Port-1    │
│                          │              │  D.Port-3 ←→ A2.Port-1    │
└──────────────────────────┘              └────────────────────────────┘
```

## 5. 颜色重算机制（完整设计）

### 5.1 总体设计

#### 5.1.1 设计原则

| 原则           | 说明                                                         |
| -------------- | ------------------------------------------------------------ |
| 仅宿端判定     | 颜色仅通过宿端判断，源端 Port-3 完全不参与                   |
| 仅网元间连纤   | 颜色仅针对网元间连纤（src_ne_id ≠ dst_ne_id）                |
| 缓存驱动       | 颜色判定通过本地**告警缓存 + 连纤缓存**完成，不实时调用外部 RPC |
| 两类触发       | 告警消息触发 + 连纤消息触发                                  |
| 不订阅Board    | FiberMaintService 不订阅 BoardEvents                         |
| 告警缓存唯一性 | 同一端口(board_id+port_id)同一告警类型(alarm_level)只存一条记录，但是同一端口(board_id+port_id)允许同时存在不同告警类型(alarm_level) |
| 存在即激活     | 告警缓存中存在该记录 → 该端口当前存在该级别告警；不存在 → 无该级别告警 |

#### 5.1.2 触发源总览

| 类别               | 触发事件                   | 来源                      | 影响                                   |
| ------------------ | -------------------------- | ------------------------- | -------------------------------------- |
| **告警消息** | ALARM_RAISED               | AlarmService → Stream    | 写入告警缓存 → 重算关联网元间连纤颜色 |
| **告警消息** | ALARM_CLEARED              | AlarmService → Stream    | 删除告警缓存 → 重算关联网元间连纤颜色 |
| **连纤消息** | FIBER_CREATED (网元间)     | TopologyService → Stream | 初始化新连纤颜色                       |
| **连纤消息** | FIBER_DELETED (网元间)     | TopologyService → Stream | 从缓存/统计中移除                      |
| **连纤消息** | FIBER_CREATED (网元内)     | TopologyService → Stream | 场景变更 → 重算关联网元间连纤         |
| **连纤消息** | FIBER_DELETED (网元内)     | TopologyService → Stream | 场景变更 → 重算关联网元间连纤         |
| **启动同步** | Pull Call + BatchGetFibers | 自身                      | 全量初始化                             |

### 5.2 FiberMaintService 本地缓存设计

#### 5.2.1 连纤缓存（方案C，Q11）

##### 设计原则

FiberMaintService 在本地维护**全量连纤信息缓存**，解决 FIBER_DELETED 事件携带信息不足的问题。

##### 数据结构

```cpp
// 内存缓存（进程内）
struct FiberCacheEntry {
    int32_t fiber_id;
    int32_t src_board_id;
    int8_t  src_port_id;
    int32_t src_ne_id;
    int32_t dst_board_id;
    int8_t  dst_port_id;
    int32_t dst_ne_id;
    bool    is_inter_ne;  // src_ne_id != dst_ne_id
};

// 索引
std::unordered_map<int32_t, FiberCacheEntry> fiber_by_id_;           // fiber_id → FiberCacheEntry
std::unordered_multimap<std::pair<int32_t,int8_t>, int32_t> fiber_by_port_;  // (board_id,port_id) → fiber_id[]（双向）
```

##### 缓存维护时机

| 时机          | 操作     | 说明                                                                       |
| ------------- | -------- | -------------------------------------------------------------------------- |
| 服务启动      | 全量加载 | TopologyService.BatchGetFibers 获取所有连纤，写入缓存                      |
| FIBER_CREATED | INSERT   | 收到事件后调用 GetFiber 获取完整信息，写入缓存                             |
| FIBER_DELETED | 先读后删 | 收到事件后**从缓存读取**完整信息（此时DB已删除），处理完后从缓存移除 |
| 断线重连      | 全量刷新 | 重新拉取全量连纤，重建缓存                                                 |

##### FIBER_DELETED 处理流程（方案C）

```
TopologyService → FiberEvent {event_type=FIBER_DELETED, fiber_id=2001}
  → FiberMaintService 接收
  → 从本地缓存 fiber_by_id_[2001] 获取完整 FiberCacheEntry
    ← {src_board_id=5, src_port_id=2, dst_board_id=1, dst_port_id=1, src_ne_id=100, dst_ne_id=100}
  → [处理颜色重算逻辑]
  → 从缓存中删除 fiber_by_id_.erase(2001)
```

#### 5.2.2 告警缓存（重新设计）

##### 设计原则

| 原则                     | 说明                                                                            |
| ------------------------ | ------------------------------------------------------------------------------- |
| **唯一性**         | 同一端口（board_id + port_id）同一告警类型（alarm_level）**只存一条记录**，但是同一端口(board_id+port_id)允许同时存在不同告警类型(alarm_level) |
| **存在即激活**     | 缓存中**存在**该记录 → 表示该端口当前存在该级别告警                      |
| **不存在即无告警** | 缓存中**不存在**该记录 → 表示该端口当前无该级别告警                      |
| **颜色判定依据**   | 颜色计算时，检查缓存中是否存在对应端口的告警记录来判定                          |
| **与DB对齐**       | 与`current_alarms` 表 PK(board_id, port_id, alarm_level) 一一对应             |

##### 数据结构

```cpp
// ═══════════════════════════════════════════════════════════
// 告警缓存 Key：唯一标识一条当前告警
// 同一端口同一告警类型只存一个（与 current_alarms PK 对齐）
// ═══════════════════════════════════════════════════════════
struct AlarmCacheKey {
    int32_t board_id;      // 单盘ID
    int8_t  port_id;       // 端口编号
    int8_t  alarm_level;   // 告警级别: 1=CRITICAL, 2=MINOR

    bool operator==(const AlarmCacheKey& o) const {
        return board_id == o.board_id
            && port_id  == o.port_id
            && alarm_level == o.alarm_level;
    }
};

struct AlarmCacheKeyHash {
    size_t operator()(const AlarmCacheKey& k) const {
        return std::hash<int64_t>()(
            (static_cast<int64_t>(k.board_id) << 16)
            | (static_cast<int64_t>(k.port_id) << 8)
            | k.alarm_level
        );
    }
};

// ═══════════════════════════════════════════════════════════
// 告警缓存 Value：告警元数据
// ═══════════════════════════════════════════════════════════
struct AlarmCacheValue {
    Timestamp raised_at;   // 告警产生时间
};

// ═══════════════════════════════════════════════════════════
// 告警缓存主体
// 存在 key → 该端口存在该级别告警
// 不存在 key → 该端口无该级别告警
// ═══════════════════════════════════════════════════════════
std::unordered_map<AlarmCacheKey, AlarmCacheValue, AlarmCacheKeyHash> alarm_cache_;
```

##### 缓存操作

| 操作                     | 触发                | 行为                                                             |
| ------------------------ | ------------------- | ---------------------------------------------------------------- |
| **写入（INSERT）** | ALARM_RAISED        | `alarm_cache_[{board_id, port_id, alarm_level}] = {raised_at}` |
| **删除（DELETE）** | ALARM_CLEARED       | `alarm_cache_.erase({board_id, port_id, alarm_level})`         |
| **全量加载**       | 服务启动 / 断线重连 | Pull Call → 清空 → 逐条写入                                    |
| **查询（EXISTS）** | 颜色计算            | `alarm_cache_.count({board_id, port_id, alarm_level}) > 0`     |

##### 告警缓存更新流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│  ALARM_RAISED 处理:                                                     │
│                                                                         │
│  AlarmEvent {event_type=ALARM_RAISED, board_id=2, port_id=1,           │
│              alarm_level=CRITICAL(1), timestamp=T1}                     │
│                                                                         │
│  → Step 1: 写入告警缓存（幂等，已存在则覆盖 raised_at）                 │
│      alarm_cache_[{2, 1, 1}] = {raised_at: T1}                         │
│                                                                         │
│  → Step 2: 触发颜色重算                                                │
│                                                                         │
│  此时缓存状态:                                                          │
│    {2, 1, 1} → 存在 → 端口(2,1)有紧急告警                              │
│    {2, 1, 2} → 不存在 → 端口(2,1)无次要告警                            │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  ALARM_CLEARED 处理:                                                    │
│                                                                         │
│  AlarmEvent {event_type=ALARM_CLEARED, board_id=2, port_id=1,          │
│              alarm_level=CRITICAL(1)}                                   │
│                                                                         │
│  → Step 1: 删除告警缓存                                                │
│      alarm_cache_.erase({2, 1, 1})                                     │
│                                                                         │
│  → Step 2: 触发颜色重算                                                │
│                                                                         │
│  此时缓存状态:                                                          │
│    {2, 1, 1} → 不存在 → 端口(2,1)无紧急告警                            │
│    {2, 1, 2} → 若存在 → 端口(2,1)仍有次要告警                          │
└─────────────────────────────────────────────────────────────────────────┘
```

##### 颜色判定 — 告警缓存查询接口

```cpp
// ═══════════════════════════════════════════════════════════
// 查询指定端口是否存在指定级别告警
// 返回 true → 存在该告警（缓存中有记录）
// 返回 false → 不存在（缓存中无记录）
// ═══════════════════════════════════════════════════════════
bool has_alarm(int32_t board_id, int8_t port_id, int8_t alarm_level) {
    AlarmCacheKey key{board_id, port_id, alarm_level};
    return alarm_cache_.count(key) > 0;
}

// ═══════════════════════════════════════════════════════════
// 查询指定端口的告警摘要（用于颜色计算）
// ═══════════════════════════════════════════════════════════
struct PortAlarmSummary {
    bool has_critical;   // 是否存在紧急告警
    bool has_minor;      // 是否存在次要告警
};

PortAlarmSummary get_port_alarm_summary(int32_t board_id, int8_t port_id) {
    return {
        .has_critical = has_alarm(board_id, port_id, 1),  // CRITICAL
        .has_minor    = has_alarm(board_id, port_id, 2)   // MINOR
    };
}
```

##### 颜色计算中的告警缓存使用示例

```cpp
// ─── 场景1：宿端是有源盘 ───
PortAlarmSummary dst_alarm = get_port_alarm_summary(dst_board_id, 1);
if (dst_alarm.has_critical)      → 🔴 红色
else if (dst_alarm.has_minor)    → 🟡 黄色
else                             → 🟢 绿色

// ─── 场景2 情况A：宿端Port-2有源盘B + Port-3有源盘A2 ───
PortAlarmSummary alarm_B  = get_port_alarm_summary(board_B, 1);
PortAlarmSummary alarm_A2 = get_port_alarm_summary(board_A2, 1);

if (alarm_B.has_critical && alarm_A2.has_critical)  → 🔴 红色
else if (alarm_B.has_minor || alarm_A2.has_minor
         || (alarm_B.has_critical && alarm_A2.has_minor)
         || (alarm_A2.has_critical && alarm_B.has_minor))  → 🟡 黄色
else if (alarm_B.has_critical && !alarm_A2.has_critical && !alarm_A2.has_minor)  → 🟢 绿色
else if (alarm_A2.has_critical && !alarm_B.has_critical && !alarm_B.has_minor)   → 🟢 绿色
else  → 🟢 绿色

// ─── 场景2 情况B：仅宿端Port-2有源盘B ───
PortAlarmSummary alarm_B = get_port_alarm_summary(board_B, 1);
if (alarm_B.has_critical)      → 🔴 红色
else if (alarm_B.has_minor)    → 🟡 黄色
else                           → 🟢 绿色

// ─── 场景2 情况C：宿端Port-2空闲 ───
→ 🟢 绿色（固定，无需查缓存）
```

##### 告警缓存完整生命周期

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    alarm_cache_ 生命周期                                 │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ 服务启动                                                        │   │
│  │   → Pull Call 获取全量当前告警                                  │   │
│  │   → 清空 alarm_cache_                                          │   │
│  │   → 逐条写入: alarm_cache_[{b,p,l}] = {raised_at}             │   │
│  │   示例:                                                         │   │
│  │     {2, 1, 1} → {raised_at: 2026-07-20 10:00}  // B紧急       │   │
│  │     {2, 1, 2} → {raised_at: 2026-07-20 10:05}  // B次要       │   │
│  │     {5, 1, 1} → {raised_at: 2026-07-20 11:00}  // A2紧急      │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│                              ▼                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ 运行中 — ALARM_RAISED                                          │   │
│  │   AlarmEvent{board=2, port=1, level=1, RAISED}                 │   │
│  │   → alarm_cache_[{2,1,1}] = {raised_at: NOW}  // 写入/覆盖    │   │
│  │   → 触发颜色重算                                               │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│                              ▼                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ 运行中 — ALARM_CLEARED                                         │   │
│  │   AlarmEvent{board=2, port=1, level=1, CLEARED}                │   │
│  │   → alarm_cache_.erase({2,1,1})  // 删除                      │   │
│  │   → 触发颜色重算                                               │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│                              ▼                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ 断线重连                                                        │   │
│  │   → Pull Call 全量同步                                          │   │
│  │   → 清空 alarm_cache_                                          │   │
│  │   → 重新逐条写入                                               │   │
│  │   → 全量重算颜色                                               │   │
│  └─────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────┘
```

##### 告警缓存与 current_alarms 表对应关系

| 缓存操作                        | 对应 DB 操作                                     | 说明       |
| ------------------------------- | ------------------------------------------------ | ---------- |
| `alarm_cache_[{b,p,l}] = {t}` | `INSERT INTO current_alarms (b,p,l,raised_at)` | 一一对应   |
| `alarm_cache_.erase({b,p,l})` | `DELETE FROM current_alarms WHERE b,p,l`       | 一一对应   |
| `alarm_cache_.count({b,p,l})` | `SELECT EXISTS(... WHERE b,p,l)`               | 存在性判断 |
| 全量加载                        | `SELECT * FROM current_alarms`                 | Pull Call  |

> ⚠️ 缓存与 DB 保持**最终一致**。正常运行时通过事件流实时同步；异常时通过断线重连全量刷新恢复。

### 5.3 告警消息触发颜色重算（ALARM_RAISED / ALARM_CLEARED）

#### 5.3.1 统一处理流程

```
AlarmEvent {event_type, board_id, port_id, alarm_level, timestamp}
  │
  ├─ Step 1: 更新告警缓存
  │    ├─ ALARM_RAISED:  alarm_cache_[{board_id, port_id, alarm_level}] = {timestamp}
  │    └─ ALARM_CLEARED: alarm_cache_.erase({board_id, port_id, alarm_level})
  │
  ├─ Step 2: 两跳寻路，找到受影响的网元间连纤
  │    → 从连纤缓存 fiber_by_port_ 查找
  │    → [第一跳结果判断]:
  │       ├─ 直接是网元间连纤 → 场景1，单跳完成
  │       ├─ 是网元内连纤，对端是无源盘Port-2或Port-3 → 需第二跳
  │       │    → 从 fiber_by_port_ 查找网元间连纤
  │       └─ 无关联连纤 / 对端是有源盘 → 跳过
  │
  ├─ Step 3: 判断告警端口在网元间连纤中的角色
  │    → 仅当告警端口属于**宿端**链路时才影响颜色
  │    → 源端告警 → 跳过（颜色仅看宿端）
  │
  ├─ Step 4: 判定场景类型
  │    → 宿端是有源盘 → 场景1
  │    → 宿端是无源盘 → 场景2
  │       → 检查宿端Port-2是否有连纤（从连纤缓存）
  │          → 无 → 情况C（绿色）
  │          → 有 → 检查Port-3
  │             → Port-3有连纤 → 情况A
  │             → Port-3无连纤 → 情况B
  │
  ├─ Step 5: 从告警缓存读取宿端相关端口告警（不调用RPC）
  │    → 场景1: get_port_alarm_summary(宿端有源盘.board_id, 1)
  │    → 场景2情况A: get_port_alarm_summary(B) + get_port_alarm_summary(A2)
  │    → 场景2情况B: get_port_alarm_summary(B)
  │    → 场景2情况C: 无需读取（直接绿色）
  │
  ├─ Step 6: 按颜色规则计算新颜色
  │
  └─ Step 7: 比较新旧颜色
       → 变化: 写 fiber_color_changes + 更新 fiber_colors + 推送 WebSocket
       → 未变: 无操作
```

#### 5.3.2 两跳寻路详细说明

**场景1（单跳）**：

```
AlarmEvent(有源盘B, Port-1)
  → fiber_by_port_ → 网元间连纤 F001 (A.Port-1 ↔ B.Port-1)
  → B 是 dst（宿端）→ 影响颜色
  → 场景1
  → 查缓存: get_port_alarm_summary(B.board_id, 1)
     → has_alarm(B, 1, CRITICAL)?  → alarm_cache_.count({B,1,1})
     → has_alarm(B, 1, MINOR)?     → alarm_cache_.count({B,1,2})
```

**场景2（两跳）— B有源盘告警**：

```
AlarmEvent(有源盘B, Port-1)
  → fiber_by_port_ → 网元内连纤 F002 (B.Port-1 ↔ D.Port-2)
  → 对端是无源盘D的Port-2 → 第二跳
  → fiber_by_port_ → 网元间连纤 F001 (C.Port-1 ↔ D.Port-1)
  → D 是宿端 → B 是 D.Port-2 所连 → 参与颜色
  → 场景2 → 检查 D.Port-3:
     → fiber_by_port_ 有连纤 → 情况A → 找 A2
     → fiber_by_port_ 无连纤 → 情况B
  → 查缓存:
     → get_port_alarm_summary(B.board_id, 1)   // B的告警
     → [情况A] get_port_alarm_summary(A2.board_id, 1)  // A2的告警
```

**场景2（两跳）— A2有源盘告警**：

```
AlarmEvent(有源盘A2, Port-1)
  → fiber_by_port_ → 网元内连纤 F003 (A2.Port-1 ↔ D.Port-3)
  → 对端是无源盘D的Port-3 → 第二跳
  → fiber_by_port_ → 网元间连纤 F001
  → D 是宿端 → A2 是 D.Port-3 所连 → 参与颜色（情况A）
  → 查缓存:
     → get_port_alarm_summary(A2.board_id, 1)  // A2的告警
     → get_port_alarm_summary(B.board_id, 1)   // B的告警
```

**源端告警（跳过）**：

```
AlarmEvent(有源盘A, Port-1)  // A 是源端有源盘
  → fiber_by_port_ → 网元内连纤 (A ↔ C.Port-2)
  → 第二跳 → fiber_by_port_ → 网元间连纤 F001
  → A 属于源端链路（C是源无源盘）→ ⚠️ 源端告警不影响颜色 → 跳过
```

#### 5.3.3 寻路判断规则汇总

| 第一跳结果                      | 对端端口 | 处理                                      |
| ------------------------------- | -------- | ----------------------------------------- |
| 网元间连纤，本端口是 dst        | —       | 场景1，宿端告警，重算                     |
| 网元间连纤，本端口是 src        | —       | 源端告警，**跳过**                  |
| 网元内连纤，对端是无源盘 Port-2 | Port-2   | 第二跳→Port-1→网元间连纤，判断宿端/源端 |
| 网元内连纤，对端是无源盘 Port-3 | Port-3   | 第二跳→Port-1→网元间连纤，判断宿端/源端 |
| 网元内连纤，对端是有源盘        | —       | 跳过（有源盘无Port-1网元间连纤）          |
| 无关联连纤                      | —       | 跳过                                      |

### 5.4 连纤消息触发颜色重算（FIBER_CREATED / FIBER_DELETED）

#### 5.4.1 统一处理流程

```
FiberEvent {event_type, fiber_id}
  │
  ├─ [FIBER_CREATED]:
  │    → TopologyService.GetFiber(fiber_id) → FiberInfo
  │    → 写入连纤缓存
  │    → 判断连纤类型:
  │       ├─ 网元间连纤 → 初始化颜色（见 §5.4.2）
  │       └─ 网元内连纤 → 场景变更重算（见 §5.4.3）
  │
  └─ [FIBER_DELETED]:
       → 从连纤缓存读取完整信息（DB已删除）
       → 判断连纤类型:
          ├─ 网元间连纤 → 移除处理（见 §5.4.4）
          └─ 网元内连纤 → 场景变更重算（见 §5.4.5）
       → 从连纤缓存删除
```

#### 5.4.2 网元间连纤创建 — 初始化颜色

```
FIBER_CREATED (网元间连纤 F_NEW)
  → 判定场景:
     → 宿端是有源盘 → 场景1
     → 宿端是无源盘 → 场景2 → 判断情况A/B/C
  → 从告警缓存读取宿端相关告警:
     → 场景1: get_port_alarm_summary(宿端有源盘, 1)
     → 场景2A: get_port_alarm_summary(B, 1) + get_port_alarm_summary(A2, 1)
     → 场景2B: get_port_alarm_summary(B, 1)
     → 场景2C: 无需查询
  → 计算初始颜色
  → INSERT fiber_colors (fiber_id, color, scene_type, scenario_case)
  → 若为红/黄: INSERT fiber_color_changes + 推送 WebSocket
```

#### 5.4.3 网元内连纤创建 — 场景变更重算

| 创建类型                | 场景变更         | 处理                                             |
| ----------------------- | ---------------- | ------------------------------------------------ |
| 有源盘 ↔ 无源盘 Port-2 | 情况C → 情况A/B | 查Port-1关联网元间连纤 → 从告警缓存读取 → 重算 |
| 有源盘 ↔ 无源盘 Port-3 | 情况B → 情况A   | 查Port-1关联网元间连纤 → 从告警缓存读取 → 重算 |

```
FIBER_CREATED (网元内连纤: 有源盘X ↔ 无源盘D.Port-2)
  → 从连纤缓存 fiber_by_port_ 查找网元间连纤
    ← [F001] 或 空
  → 若空: 直接跳过（Q21: Port-1无网元间连纤时跳过）
  → 若找到 F001:
     → 场景变更: 情况C → 情况A/B
     → 从告警缓存读取有源盘X的告警（新连接的有源盘）
     → 检查 D.Port-3 状态 → 确定情况A或B
     → 若情况A: 还需读 A2 的告警缓存
     → 计算新颜色
     → 比较并更新
```

#### 5.4.4 网元间连纤删除 — 移除处理

```
FIBER_DELETED (网元间连纤 F001)
  → 从连纤缓存读取 F001 信息
  → 从 fiber_colors 删除 F001
  → 若原为红/黄: 更新统计 + 推送 WebSocket (fiber.color_change → removed)
  → 从连纤缓存删除 F001
```

#### 5.4.5 网元内连纤删除 — 场景变更重算

| 删除类型                | 场景变更         | 处理                  |
| ----------------------- | ---------------- | --------------------- |
| 有源盘 ↔ 无源盘 Port-2 | 情况A/B → 情况C | 强制绿色              |
| 有源盘 ↔ 无源盘 Port-3 | 情况A → 情况B   | 从告警缓存读B → 重算 |

```
FIBER_DELETED (网元内连纤: 有源盘B ↔ 无源盘D.Port-2)
  → 从连纤缓存读取被删连纤信息
  → 识别: 无源盘D 的 Port-2 被释放
  → 从 fiber_by_port_ 查找网元间连纤
    ← [F001] 或 空
  → 若空: 跳过
  → 若找到 F001:
     → 场景变更: → 情况C（Port-2空闲）
     → 新颜色 = 🟢 绿色（强制）
     → 比较并更新
FIBER_DELETED (网元内连纤: 有源盘A2 ↔ 无源盘D.Port-3)
  → 识别: 无源盘D 的 Port-3 被释放
  → 从 fiber_by_port_ 查找网元间连纤 → F001
  → 场景变更: 情况A → 情况B
  → 从告警缓存读取有源盘B的告警: get_port_alarm_summary(B, 1)
  → 按情况B规则计算新颜色
  → 比较并更新
```

#### 5.4.6 连纤消息 — 场景变更矩阵汇总

| 操作 | 连纤类型           | 影响端口                    | 场景变更 | 颜色影响               |
| ---- | ------------------ | --------------------------- | -------- | ---------------------- |
| 创建 | 网元内（↔Port-2） | 宿无源盘 Port-2: 空闲→占用 | C → A/B | 可能 绿→红/黄         |
| 创建 | 网元内（↔Port-3） | 宿无源盘 Port-3: 空闲→占用 | B → A   | 判定逻辑变更           |
| 删除 | 网元内（↔Port-2） | 宿无源盘 Port-2: 占用→空闲 | A/B → C | 强制变绿               |
| 删除 | 网元内（↔Port-3） | 宿无源盘 Port-3: 占用→空闲 | A → B   | 判定逻辑变更           |
| 创建 | 网元间             | 新连纤                      | 新增     | 初始化（基于告警缓存） |
| 删除 | 网元间             | 被删连纤                    | 移除     | 从统计移除             |

### 5.5 颜色计算规则（完整决策表）

### 5.6 并发颜色重算 — 锁机制（Q17，待进一步设计）

> ⚠️ 框架设计，具体实现待后续细化。

#### 5.6.1 问题场景

| 场景                                 | 风险                     |
| ------------------------------------ | ------------------------ |
| 同一连纤同时收到两个告警事件         | 两次重算结果可能互相覆盖 |

| 同一无源盘 Port-2 和 Port-3 同时变更 | 两次场景变更交叉执行     |

| 版本号   | 每次重算携带版本号，写入时 CAS 校验          |
| 最终一致 | 允许短暂不一致，后到事件覆盖先到结果         |

## 6. 断线重连与增量补偿机制（Q16）

### 6.1 内部 gRPC Stream 断线重连

| 订阅方            | 订阅源                               | 断线检测                | 重连策略                             | 补偿机制                                                          |
| ----------------- | ------------------------------------ | ----------------------- | ------------------------------------ | ----------------------------------------------------------------- |
| FiberMaintService | AlarmService.SubscribeAlarmEvents    | 心跳超时 / stream error | 指数退避重连（1s→2s→4s→...→60s） | 重连后 Pull Call → 清空 alarm_cache_ → 全量重建 → 全量重算颜色 |
| FiberMaintService | TopologyService.SubscribeFiberEvents | 心跳超时 / stream error | 指数退避重连                         | 重连后 BatchGetFibers → 重建连纤缓存 → 全量重算                 |
| TopologyService   | BoardService.SubscribeBoardEvents    | 心跳超时 / stream error | 指数退避重连                         | 重连后 BatchGetBoards 刷新缓存                                    |
| API Gateway       | 各服务 Stream                        | 心跳超时 / stream error | 指数退避重连                         | 重连后无需补偿（仅转发增量）                                      |

### 6.2 FiberMaintService 断线重连完整流程

```
[检测到 AlarmService Stream 断开]
  → 标记 alarm_stream_disconnected = true
  → [暂停处理告警事件队列]
  → [指数退避重连]
  → [重连成功]
  → AlarmService.CreatePullCall(ports=[], include_history=false)
  → [轮询] GetPullCallResult → 全量当前告警
  → alarm_cache_.clear()
  → 逐条写入 alarm_cache_[{b,p,l}] = {raised_at}
  → [重新计算所有网元间连纤颜色（读 alarm_cache_）]
  → [更新 fiber_colors]
  → 标记 alarm_stream_disconnected = false
  → [恢复处理事件队列]

[检测到 TopologyService Stream 断开]
  → 标记 topo_stream_disconnected = true
  → [指数退避重连]
  → [重连成功]
  → TopologyService.BatchGetFibers([全部])
  → [重建连纤缓存 fiber_by_id_, fiber_by_port_]
  → [重新计算所有网元间连纤颜色（读 alarm_cache_）]
  → 标记 topo_stream_disconnected = false
```

### 6.3 前端 WebSocket 断线重连（Q23）

| 步骤 | 说明                                             |
| ---- | ------------------------------------------------ |
| 1    | 客户端检测断线（心跳超时 30s）                   |
| 2    | 指数退避重连（1s, 2s, 4s, ... 最大 60s）         |

| BatchGetCurrentAlarms 中某端口无告警      | 该条返回空列表                      |

响应结构示例：

```protobuf
message BatchGetFibersResponse {
    repeated FiberInfoResult results = 1;  // 与请求顺序一一对应
}

message FiberInfoResult {
    bool found = 1;              // 是否存在
    FiberInfo fiber = 2;         // found=true 时有值
    string error_message = 3;    // found=false 时的错误信息
}
```

### 15.2 约束规则汇总

| 编号 | 规则                                                         |
| ---- | ------------------------------------------------------------ |
| R-01 | 一端口一连纤                                                 |
| R-02 | 有源盘单端口，一生一条连纤                                   |
| R-03 | 无源盘三端口：Port-1(网元间) + Port-2(主) + Port-3(辅)       |
| R-04 | 创建校验：端口存在、空闲、非同一单盘、用途匹配               |
| R-05 | 删除释放（port_occupied = false）                            |
| R-06 | 单盘删除级联（调用 TopologyService RPC）                     |
| R-07 | 不可修改                                                     |
| R-08 | 光纤维护服务仅操作网元间连纤                                 |
| R-09 | ne_id 自动记录                                               |
| R-10 | 拓扑统一管理                                                 |
| R-11 | Port-2 不可空闲                                              |
| R-12 | 当前仅两种场景                                               |
| R-13 | 连纤有方向性（src→dst）                                      |
| R-14 | 无源盘端口无告警/性能数据                                    |
| R-15 | 颜色判断仅基于宿端，源端 Port-3 不参与                       |
| R-16 | 连纤增删触发颜色重算（场景变更）                             |
| R-17 | FiberMaintService 不订阅 BoardEvents                         |
| R-18 | GetFibersByPort 双向匹配                                     |
| R-19 | fiber_colors 仅存储网元间连纤                                |
| R-20 | 性能归档后清空 current 表                                    |
| R-21 | 批量查询不存在的 ID 标记 null/error，不整体失败              |
| R-22 | BoardEvent 在所有级联操作完成后最后推送                      |
| R-23 | 情况A单侧紧急=绿色（有意设计，避免误报）                     |
| R-24 | 颜色判定通过告警缓存完成，不实时调用 AlarmService RPC        |
| R-25 | 告警消息先更新缓存再触发重算                                 |
| R-26 | 告警缓存唯一性：同一端口(board_id+port_id)同一告警类型(alarm_level)只存一条，但是同一端口(board_id+port_id)允许同时存在不同告警类型(alarm_level) |
| R-27 | 告警缓存存在即激活：缓存中有记录=该告警存在，无记录=该告警不存在 |
| R-28 | 告警缓存与 current_alarms 表 PK 一一对应                     |
