## 一、问题陈述

### 1.1 要解决的问题

| 编号 | 问题                                                         | 严重程度 | 影响                        |
| ---- | ------------------------------------------------------------ | -------- | --------------------------- |
| P-1  | 每条告警触发两跳寻路（遍历fiber_cache_找受影响连纤），O(n)复杂度 | 高       | 告警风暴时CPU飙升           |
| P-2  | 颜色计算采用全量读取alarm_cache_方式，每次重新统计           | 高       | 无效计算量大                |
| P-3  | 告警处理与DB写入/WebSocket推送同步耦合                       | 高       | 单条处理延迟3~6ms，吞吐受限 |
| P-4  | 场景2多端口告警存在中间态问题                                | 中       | 可能产生错误颜色闪烁        |
| P-5  | 闪断告警（RAISED/CLEARED快速交替）产生大量无效计算           | 中       | CPU浪费，DB写入放大         |
| P-6  | 无背压机制，告警风暴下接收队列可能溢出                       | 高       | OOM或告警丢失               |
| P-7  | 场景知识硬编码在多处（枚举、结构体、if/else分支）            | 中       | 新增场景需改动6+处代码      |
| P-8  | 连纤增删事件与告警事件存在竞态                               | 中       | 可能读到不一致状态          |

### 1.2 问题根因分析

```
┌─────────────────────────────────────────────────────────────────┐
│                        根因分析图                                 │
│                                                                  │
│  P-1 两跳寻路 ──────┐                                           │
│  P-2 全量重算 ──────┤──→ 每条告警处理耗时过长 ──→ 吞吐不足       │
│  P-3 同步IO ────────┘                                           │
│                                                                  │
│  P-4 中间态 ──────────→ 多端口告警非原子处理 ──→ 颜色闪烁        │
│                                                                  │
│  P-5 闪断 ───────────→ 无抑制机制 ──→ 无效计算放大               │
│                                                                  │
│  P-6 无背压 ─────────→ 无界队列 ──→ 风暴下OOM                    │
│                                                                  │
│  P-7 硬编码 ─────────→ 违反开闭原则 ──→ 扩展成本高               │
│                                                                  │
│  P-8 竞态 ───────────→ 多线程访问共享状态 ──→ 数据不一致          │
└─────────────────────────────────────────────────────────────────┘
```

## 二、现状分析

### 2.1 当前实现架构（基于 fiber_maint_service_impl.cpp）

```
┌─────────────────────────────────────────────────────────────────┐
│              当前 FiberMaintServiceImpl 架构                      │
│                                                                  │
│  gRPC Stream ──→ OnAlarmEvent() ──→ 处理逻辑（同步）            │
│                       │                                          │
│                       ├──→ 更新 alarm_cache_（加锁）             │
│                       ├──→ 遍历 fiber_cache_ 找受影响连纤 O(n)   │
│                       ├──→ 全量读 alarm_cache_ 统计告警数        │
│                       ├──→ 颜色决策（if/else硬编码）             │
│                       ├──→ 比较 old vs new                       │
│                       ├──→ DB写入（同步）                        │
│                       └──→ WebSocket推送（同步）                 │
│                                                                  │
│  OnFiberCreated() ──→ 更新 fiber_cache_ ──→ 触发颜色计算        │
│  OnFiberDeleted() ──→ 读取信息 ──→ 删除 ──→ 清理DB             │
│                                                                  │
│  问题：                                                          │
│  ① 所有操作在同一调用栈中同步完成                                │
│  ② 每条告警 O(n) 遍历                                           │
│  ③ 每次颜色计算全量统计                                         │
│  ④ DB/WS 阻塞告警消费                                           │
│  ⑤ 场景1/2 硬编码在 CalculateColor() 中                         │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 当前代码中的关键耦合点

| 代码位置                | 耦合内容                                 |
| ----------------------- | ---------------------------------------- |
| `CalculateFiberColor()` | 硬编码场景1/场景2的if/else分支           |
| `alarm_cache_` 结构     | 固定字段 `critical_count`, `minor_count` |
| `FindAffectedFibers()`  | 遍历全部fiber_cache_，O(n)               |
| `OnAlarmEvent()`        | 同步调用DB写入和WS推送                   |
| `SceneType` 枚举        | 固定 `SCENE_1`, `SCENE_2`                |
| `ScenarioCase` 枚举     | 固定 `CASE_A`, `CASE_B`, `CASE_C`        |

### 2.3 性能瓶颈量化

| 操作                         | 当前耗时                     | 调用频率     | 瓶颈等级 |
| ---------------------------- | ---------------------------- | ------------ | -------- |
| 两跳寻路（遍历fiber_cache_） | 0.05~0.5ms（取决于连纤数量） | 每条告警     | ⚠️ 高     |
| 全量统计alarm_cache_         | 0.02~0.1ms                   | 每次颜色计算 | ⚠️ 中     |
| DB写入（单条INSERT/UPDATE）  | 2~5ms                        | 每次颜色变化 | ❌ 极高   |
| WebSocket推送                | 0.5~1ms                      | 每次颜色变化 | ⚠️ 中     |
| **单条告警总处理时间**       | **3~6ms**                    | —            | —        |
| **理论吞吐上限**             | **~200条/秒**                | —            | ❌ 不足   |

## 三、设计目标

### 3.1 性能目标

| 指标                                   | 当前值    | 目标值       | 提升倍数 |
| -------------------------------------- | --------- | ------------ | -------- |
| 单条告警处理延迟（Layer1）             | 3~6ms     | < 0.01ms     | 300x+    |
| 端到端延迟（告警→颜色推送）            | 3~6ms     | < 65ms       | —        |
| 告警消费吞吐                           | ~200条/秒 | > 50000条/秒 | 250x     |
| 告警风暴（20000条/秒）下CRITICAL丢失率 | 可能丢失  | 0%           | —        |
| 闪断告警无效计算过滤率                 | 0%        | > 90%        | —        |
| 接收队列溢出风险                       | 存在      | 消除         | —        |

### 3.2 可扩展性目标

| 指标                   | 当前 | 目标             |
| ---------------------- | ---- | ---------------- |
| 新增场景需修改文件数   | 6+   | 1（新增文件）    |
| 新增场景需修改引擎代码 | 是   | 否               |
| 场景规则修改影响范围   | 全局 | 仅对应Scenario类 |

### 3.3 正确性目标

| 指标                  | 保证                        |
| --------------------- | --------------------------- |
| 同端口告警时序        | 串行消费天然保证            |
| 场景2多端口一致性     | 聚合窗口 + 单线程结构性保证 |
| 连纤增删与告警无竞态  | 同一串行流顺序处理          |
| 颜色未变不通知        | 计算后比较，相同则丢弃      |
| FIBER_DELETED先读后删 | 方案C保持不变               |

### 4.2 线程模型

| 线程                 | 职责                            | 数量 | 同步机制           |

## 五、详细设计

### 5.1 Layer 0：有界接收缓冲

#### 5.1.1 解决的问题

> **P-6**：当前无背压机制，告警风暴下事件无限堆积导致OOM。

#### 5.1.2 设计方案

```
┌─────────────────────────────────────────────────────────────┐
│                    Ring Buffer 设计                           │
│                                                              │
│  容量：50000 条事件                                          │
│  类型：SPSC（单生产者单消费者）无锁环形缓冲                   │
│  生产者：gRPC Stream 读取线程                                │
│  消费者：Layer 1 消费线程                                    │
│                                                              │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐                 │
│  │ E │ E │ E │   │   │   │   │ E │ E │ E │  ← 环形         │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘                 │
│        ↑ write_pos              ↑ read_pos                   │
│                                                              │
│  背压策略：                                                  │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  水位 < 60%  │ 正常消费                              │   │
│  │  60% ~ 80%   │ WARN日志，跳过慢路径                  │   │
│  │  80% ~ 95%   │ 丢弃MINOR告警，保留CRITICAL+连纤事件  │   │
│  │  > 95%       │ 覆盖最旧事件 + 标记"需全量重算"       │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  不可丢弃：CRITICAL告警、FIBER_CREATED、FIBER_DELETED        │
└─────────────────────────────────────────────────────────────┘
```

#### 5.1.3 达到的效果

- 内存使用有上界：50000 × 200字节 ≈ 10MB
- 极端风暴下不OOM
- CRITICAL告警100%不丢失
- 丢弃的MINOR通过风暴后全量重算补偿

### 5.2 Layer 1：串行消费引擎

#### 5.2.1 解决的问题

> **P-1**（两跳寻路）、**P-2**（全量重算）、**P-5**（闪断）、**P-8**（竞态）

#### 5.2.2 核心设计：预建端口依赖图

**替代当前的 `FindAffectedFibers()` 遍历逻辑：**

```
当前实现（O(n)遍历）：
  OnAlarmEvent(board_id, port_id):
      for each fiber in fiber_cache_:        ← 遍历所有连纤
          if fiber.dst_board == board_id:    ← 逐一匹配
              affected.push(fiber)

优化后（O(1)查表）：
  OnAlarmEvent(board_id, port_id):
      bindings = port_dependency_map_[{board_id, port_id}]  ← 直接定位
      for each binding in bindings:
          update_slot(binding.fiber_id, binding.slot_index)
```

**依赖图数据结构：**

```
port_dependency_map_: unordered_map<PortKey, vector<SlotBinding>>

PortKey { int32_t board_id; int32_t port_id; }

SlotBinding {
    int32_t fiber_id;       // 受影响的网元间连纤
    int32_t slot_index;     // 更新ColorContext的哪个slot
    int8_t  alarm_level;    // 匹配的告警级别
}
```

**依赖图构建（启动时 + 连纤增删时维护）：**

```
┌─────────────────────────────────────────────────────────────────┐
│                  依赖图构建流程                                    │
│                                                                  │
│  对于网元间连纤 fiber_200:                                        │
│    src: NE1/Board10/Port1                                        │
│    dst: NE2/Board20/Port1 (有源盘)                               │
│                                                                  │
│  场景1（dst有源盘）：                                             │
│    port_dependency_map_[{20, 1}] += {fiber_200, slot=0, CRITICAL}│
│    port_dependency_map_[{20, 1}] += {fiber_200, slot=1, MINOR}   │
│                                                                  │
│  场景2（dst无源盘）：                                             │
│    Port-2 → 有源盘B(Board30):                                    │
│      port_dependency_map_[{30, 1}] += {fiber_200, slot=0, CRIT}  │
│      port_dependency_map_[{30, 1}] += {fiber_200, slot=1, MINOR} │
│    Port-3 → 有源盘A2(Board40):                                   │
│      port_dependency_map_[{40, 1}] += {fiber_200, slot=2, CRIT}  │
│      port_dependency_map_[{40, 1}] += {fiber_200, slot=3, MINOR} │
└─────────────────────────────────────────────────────────────────┘
```

#### 5.2.3 核心设计：增量ColorContext

**替代当前的全量统计逻辑：**

```
当前实现（全量统计）：
  CalculateColor(fiber_id):
      critical_count = 0
      for each alarm in alarm_cache_:       ← 遍历所有告警
          if alarm.board == fiber.dst_board:
              critical_count++              ← 重新统计
      return (critical_count > 0) ? RED : GREEN

优化后（增量维护）：
  OnAlarmEvent(RAISED, CRITICAL):
      ctx.alarm_counts[slot] += 1           ← O(1) 增量

  CalculateColor(fiber_id):
      return scenario.evaluate(ctx.alarm_counts)  ← 直接读计数
```

**ColorContext 结构（通用化）：**

```
ColorContext {
    int32_t fiber_id;
    int32_t scenario_id;              // 关联场景（注册时分配）
    vector<uint16_t> alarm_counts;    // 动态状态向量（长度由场景决定）
    FiberColor current_color;         // 当前颜色（权威值）
    bool is_dirty;                    // 是否需要重算
    int64_t dirty_since_ms;           // 标记dirty时间
}
```

#### 5.2.4 核心设计：闪断抑制

```
┌─────────────────────────────────────────────────────────────────┐
│                    闪断检测与抑制                                  │
│                                                                  │
│  每个 (board_id, port_id, alarm_level) 维护 FlapState：          │
│                                                                  │
│  时间线：                                                        │
│  t=0ms    RAISED   → flap_count=1, 正常标记dirty                 │
│  t=50ms   CLEARED  → flap_count=2, 正常标记dirty                 │
│  t=100ms  RAISED   → flap_count=3, 正常标记dirty                 │
│  ...                                                             │
│  t=500ms  CLEARED  → flap_count=11 > 阈值10 → 进入抑制！         │
│  t=550ms  RAISED   → 抑制中：更新cache和计数，不标记dirty         │
│  t=600ms  CLEARED  → 抑制中：同上                                │
│  ...                                                             │
│  t=2600ms （连续2秒无新事件）→ 抑制解除                           │
│           → 标记一次dirty → 基于最终状态计算一次                   │

│  效果：20次闪断 → 仅触发 ~3次颜色计算（过滤85%）                  │

### 5.3 Layer 2：延迟批量颜色计算

#### 5.3.1 解决的问题

> **P-3**（同步IO阻塞）、**P-4**（场景2中间态）、**P-5**（无效计算）

#### 5.3.2 聚合窗口机制

```
┌─────────────────────────────────────────────────────────────────┐
│              聚合窗口工作原理                                      │
│                                                                  │
│  目的：让"逻辑上同时"的多条告警在一次计算中被看到                  │
│                                                                  │
│  场景2示例：                                                     │
│                                                                  │
│  t=0ms   B的CRITICAL到达 → Layer1: b_critical=1, dirty+=fiber    │
│  t=3ms   A2的CRITICAL到达 → Layer1: a2_critical=1, dirty(已有)   │
│  t=10ms  聚合窗口到期 → Layer2执行：                              │
│          读取 b_critical=1, a2_critical=1                         │
│          查表 CaseA[2][2] = RED ✓                                │
│                                                                  │
│  对比无窗口：                                                    │
│  t=0ms   B到达 → 立即计算 → b=1,a2=0 → CaseA[2][0]=GREEN ← 错误│
│  t=3ms   A2到达 → 再次计算 → b=1,a2=1 → RED                     │
│  产生 GREEN→RED 的无效闪烁                                       │
│                                                                  │
│  自适应窗口：                                                    │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ dirty_set < 100   → 窗口 10ms  （正常，低延迟）            │  │
│  │ dirty_set 100~500 → 窗口 30ms  （高压，适度合并）          │  │
│  │ dirty_set > 500   → 窗口 100ms （风暴，大量合并）          │  │
│  │ dirty_set > 2000  → 窗口 200ms （极端，最大合并）          │  │
│  └────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

#### 5.3.3 计算流程

```
┌─────────────────────────────────────────────────────────────────┐
│              Layer 2 计算流程                                     │
│                                                                  │
│  Layer2 Loop:                                                    │
│       │                                                          │
│       ▼                                                          │
│  ┌──────────────────┐                                            │
│  │ 等待通知/超时    │  wait(aggregate_window_ms)                  │
│  └────────┬─────────┘                                            │
│           ▼                                                      │
│  ┌──────────────────┐                                            │
│  │ 取出dirty_set    │  fibers = dirty_set_.steal_all()           │
│  │ （原子交换）     │  （Layer1继续写入新set，互不干扰）          │
│  └────────┬─────────┘                                            │
│           ▼                                                      │
│  ┌──────────────────┐                                            │
│  │ 分批处理         │  每批 ≤ 500 fiber                          │
│  │ （避免长占用）   │                                            │
│  └────────┬─────────┘                                            │
│           ▼                                                      │
│  ┌──────────────────────────────────────────┐                    │
│  │ 对每个 fiber_id:                         │                    │
│  │   ctx = color_contexts_[fiber_id]        │                    │
│  │   scenario = registry_.get(ctx.scenario) │                    │
│  │   new_color = scenario.evaluate(counts)  │  ← 调用场景策略    │
│  │   if new_color == ctx.current_color:     │                    │
│  │       continue  // 无变化，丢弃          │                    │
│  │   ctx.current_color = new_color          │                    │
│  │   change_queue_.push({fiber_id, old, new})│                   │
│  └──────────────────────────────────────────┘                    │
│                                                                  │
│  特点：                                                          │
│  · 纯内存操作，无IO                                              │
│  · 通过IScenario接口调用，引擎不关心具体场景逻辑                  │
│  · 无变化则丢弃（颜色未变不通知）                                │
└─────────────────────────────────────────────────────────────────┘
```

## 八、异常处理与容错

### 8.1 异常场景处理矩阵

| 异常场景                     | 检测方式          | 处理策略                   | 恢复方式        |
| ---------------------------- | ----------------- | -------------------------- | --------------- |
| gRPC Stream断连              | Read()返回false   | 停止消费，保持各Layer运行  | 重连后全量同步  |
| DB写入失败                   | 返回错误码        | 重试3次 → 写本地WAL        | DB恢复后WAL回放 |
| 计数下溢（CLEARED但count=0） | count==0且delta<0 | 告警日志 + 该fiber全量重算 | 自动恢复        |
| Ring Buffer溢出              | 水位>95%          | 覆盖最旧 + 标记需重算      | 风暴后全量重算  |
| 场景匹配失败                 | matcher返回-1     | 默认GREEN + 告警日志       | 人工介入        |
| Layer2计算异常               | try-catch         | 跳过该fiber + 告警         | 下次dirty时重算 |

class IScenario {
public:
    virtual ~IScenario() = default;

    // 场景元信息
    virtual int32_t id() const = 0;
    virtual std::string name() const = 0;
    virtual int32_t state_vector_size() const = 0;

    // 依赖解析：连纤拓扑 → 端口依赖列表
    virtual std::vector<SlotBinding> resolve_dependencies(
        const FiberInfo& fiber) = 0;

    // 颜色计算：状态向量 → 颜色
    virtual FiberColor evaluate_color(
        const std::vector<uint16_t>& alarm_counts) = 0;

    // 短路判断（默认不短路）
    virtual bool can_short_circuit(
        const ColorContext& ctx,
        int8_t event_type,
        int8_t event_level,
        int32_t slot_index) { return false; }

    // 场景匹配
    virtual bool matches(const FiberInfo& fiber) = 0;

    // 生命周期钩子（可选）
    virtual void on_fiber_created(ColorContext& ctx, const FiberInfo& fiber) {}
    virtual void on_fiber_deleted(const ColorContext& ctx, const FiberInfo& fiber) {}
};
```
