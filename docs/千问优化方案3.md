## 1. 需求背景与约束

### 1.1 业务背景

光纤网络运维系统中，每条网元间连纤（Inter-NE Fiber）需要：

- **实时颜色判定**：根据宿端链路告警状态计算健康颜色（RED/YELLOW/GREEN）
- **性能数据查询**：查询源端+宿端的光功率（OOP/IOP）
- **跨段损耗计算**：基于源端发光与宿端收光的差值
- **历史性能回溯**：按时间范围查询历史性能数据

### 1.2 颜色判定场景

```
场景1：宿端为有源盘（Active Board）
  └── 直接检查宿端 Port-1 告警

场景2：宿端为无源盘（Passive Board）
  ├── Case A：Port-2 和 Port-3 均有网元内连纤（双路保护）
  ├── Case B：仅 Port-2 有网元内连纤（单路）
  └── Case C：Port-2/3 均无网元内连纤（无保护路径）
```

### 1.3 颜色判定拓扑示意

```
场景1（宿端有源盘）：
  NE-A [Board-101/Port-1] ═══网元间连纤═══ NE-B [Board-201/Port-1]（有源盘）
  源端                                          宿端 → 直接查告警

场景2 Case A（双路保护）：
  NE-A [Board-101/Port-1] ═══网元间连纤═══ NE-B [Board-201/Port-1]（无源盘）
  源端                                          宿端
                                                 ├── Port-2 ──网元内── [Board-301/Port-1]（有源盘B）
                                                 └── Port-3 ──网元内── [Board-302/Port-1]（有源盘A2）
```

### 1.4 核心需求约束

| 编号  | 约束                                         | 设计影响                 |
| ----- | -------------------------------------------- | ------------------------ |
| R-15  | 颜色仅基于宿端判断                           | 告警查询只关注宿端链路   |
| R-23  | 情况A单侧紧急=绿色（有意设计）               | 短路规则的业务依据       |
| R-24  | 颜色判定通过告警缓存完成，不实时调RPC        | 计算必须纯内存           |
| R-25  | 告警消息先更新缓存再触发重算                 | 处理顺序不可变           |
| R-26  | 同一(board_id, port_id, alarm_level)只存一条 | 存在性模型，非计数器     |
| R-27  | 存在即激活，不存在即无告警                   | 布尔语义                 |
| R-28  | 同端口允许不同alarm_level共存                | 缓存Key必须含alarm_level |
| NF-14 | 颜色重算延迟 ≤ 3s                            | 端到端延迟上限           |
| NF-17 | 告警缓存与AlarmService最终一致               | 不可丢弃任何告警         |
| Q25   | 单侧紧急=绿色是有意设计                      | 短路逻辑正确性基础       |

### 1.5 场景2 Case A 完整决策表

| B (Port-2有源盘) | A2 (Port-3有源盘) | 颜色     | 说明               |
| ---------------- | ----------------- | -------- | ------------------ |

| CRITICAL         | MINOR             | 🟡 YELLOW | 主路中断+备路劣化  |

| 无告警           | 无告警            | 🟢 GREEN  | 正常               |

### 1.6 性能查询与颜色判定的差异

| 维度     | 颜色判定         | 性能查询               | 跨段损耗                    |
| -------- | ---------------- | ---------------------- | --------------------------- |
| 查询范围 | **仅宿端**       | **源端+宿端**          | **源端+宿端**               |
| 数据来源 | 告警缓存（内存） | PerformanceService RPC | PerformanceService RPC      |
| 后处理   | 决策表→颜色      | 值直接映射             | **差值计算**（源OOP-宿IOP） |
| 实时性   | 事件驱动（推送） | 请求驱动（拉取）       | 请求驱动（拉取）            |
| 触发方式 | 告警事件到达     | 用户/前端请求          | 用户/前端请求               |

## 2. 现有系统问题分析

### 2.1 正确性问题（P0）

| 编号  | 问题                                                         | 严重度 | 位置                             |
| ----- | ------------------------------------------------------------ | ------ | -------------------------------- |
| BUG-1 | `full_color_recalc()` 中 `std::mutex` 不可重入导致死锁       | 致命   | `calculate_color()` 内部二次加锁 |
| BUG-2 | ABBA 死锁：`GetColoredFibers()` 先锁 `color_cache_mutex_` 再锁 `fiber_cache_mutex_`，其他路径相反 | 致命   | 多处                             |
| BUG-3 | `GetFiberStatsRealtime()` 跨锁访问 `fiber_by_id_` 和 `alarm_cache_` | 高     | 数据竞争                         |
| BUG-4 | `subscribe_fiber_events()` 断线后不重连                      | 高     | 拓扑事件丢失                     |
| BUG-5 | `init_alarm_sync_async` 使用 detached thread，析构时悬空指针 | 中     | 生命周期管理                     |

### 2.2 性能问题（P1）

| 编号   | 问题                                       | 影响                |
| ------ | ------------------------------------------ | ------------------- |
| PERF-1 | 告警到达后 O(n) 遍历所有连纤寻找受影响者   | 千级连纤时 3~6ms/条 |
| PERF-2 | 颜色计算中同步 DB 写入阻塞事件处理         | 10~50ms/次          |
| PERF-3 | 无闪断抑制，设备抖动导致颜色频繁翻转       | 无效DB写入+推送风暴 |
| PERF-4 | 无短路预判，颜色不可能变化时仍执行完整计算 | 浪费CPU             |
| PERF-5 | Batch 性能接口逐条做场景判断，无去重       | 重复 RPC 查询       |

### 2.3 可维护性问题（P2）

| 编号    | 问题                                        | 影响                   |
| ------- | ------------------------------------------- | ---------------------- |
| MAINT-1 | 颜色计算逻辑硬编码在 `calculate_color()` 中 | 新增场景需修改核心函数 |
| MAINT-2 | 依赖构建逻辑与场景判断耦合                  | 违反开闭原则           |
| MAINT-3 | 6个性能接口中场景判断逻辑重复6次（~150行）  | 修改需改6处            |
| MAINT-4 | 性能查询的场景判断与颜色计算独立维护        | 可能不一致             |
| MAINT-5 | 性能查询（源+宿）与告警（仅宿）逻辑混合     | 高耦合                 |
| MAINT-6 | SQL 拼接存在注入风险                        | 安全隐患               |

### 2.4 耦合问题（P1）

```
当前状态：
  颜色计算中的场景判断："宿端告警来自哪些板卡？"
  性能查询中的场景判断："性能数据从哪些板卡查？"
  
  两处独立维护同一拓扑逻辑 → 违反 DRY
  但查询范围不同（仅宿端 vs 源+宿）→ 不能简单合并
  
  强行合并 → 高耦合（改性能影响告警）
  完全独立 → 重复代码（7处维护）
  
  正确方案：共享拓扑知识（Layer 1），分离业务查询（Layer 2/3）
```

## 3. 设计原则与目标

### 3.1 设计原则

| 原则             | 说明                                       |
| ---------------- | ------------------------------------------ |
| **正确性优先**   | 严格对齐 R-24~R-28，不丢弃任何告警事件     |
| **单线程消费**   | 所有事件串行处理，从根本上消除竞态和死锁   |
| **分层解耦**     | 共享拓扑知识，分离业务查询，各层独立演进   |
| **事件自包含**   | FIBER_CREATED 携带完整信息，消除处理时 RPC |
| **策略可扩展**   | 新增场景只需新增策略类，核心引擎零修改     |
| **依赖自声明**   | 策略声明自己依赖哪些端口，构建器通用化     |
| **计算与IO解耦** | 颜色计算纯内存，DB/推送异步批量            |
| **DRY 且低耦合** | 拓扑解析共享，业务逻辑独立                 |
| **渐进式实施**   | 分阶段交付，每阶段可独立验证和回滚         |

### 3.2 性能目标

| 指标                        | 当前       | 目标              |
| --------------------------- | ---------- | ----------------- |
| 单条告警处理延迟            | 3~6ms      | < 0.1ms（纯内存） |
| 端到端延迟（告警→颜色更新） | 15~60ms    | < 5ms             |
| 寻路复杂度                  | O(n)       | O(1)              |
| 吞吐能力                    | ~200 条/秒 | > 10,000 条/秒    |
| 闪断场景无效计算            | 100%       | < 5%（合并后）    |
| 死锁风险                    | 存在       | 消除              |
| 性能接口场景判断            | 6处重复    | 1处共享           |
| Batch RPC 去重              | 无         | 同 board 只查一次 |

### 6.1 告警缓存

```cpp
// ═══ 告警缓存 Key ═══
// 约束 R-26: 同一 (board_id, port_id, alarm_level) 只存一条
// 约束 R-28: 同端口允许不同 alarm_level 共存
struct AlarmCacheKey {
    int32_t board_id;
    int8_t  port_id;
    int8_t  alarm_level;   // CRITICAL=1, MINOR=2

    bool operator==(const AlarmCacheKey& o) const {
        return board_id == o.board_id 
            && port_id == o.port_id 
            && alarm_level == o.alarm_level;
    }
};

struct AlarmCacheKeyHash {
    size_t operator()(const AlarmCacheKey& k) const {
        size_t h = std::hash<int32_t>{}(k.board_id);
        h ^= std::hash<int8_t>{}(k.port_id) + 0x9e3779b9 + (h << 6) + (h >> 2);
        h ^= std::hash<int8_t>{}(k.alarm_level) + 0x9e3779b9 + (h << 6) + (h >> 2);
        return h;
    }
};

// ═══ 告警缓存 Value ═══
// 约束 R-27: 存在即激活，不存在即无告警
struct AlarmCacheValue {
    int64_t raised_at_ms;   // 告警产生时间戳
};

// 缓存本体
using AlarmCache = std::unordered_map<AlarmCacheKey, AlarmCacheValue, AlarmCacheKeyHash>;
```

### 7.3 拓扑解析器实现

```cpp
class FiberTopologyResolver {
    const std::unordered_map<int32_t, FiberCacheEntry>& fiber_by_id_;
    const std::unordered_multimap<PortKey, int32_t, PortKeyHash>& fiber_by_port_;
    
public:
    FiberTopologyResolver(
        const std::unordered_map<int32_t, FiberCacheEntry>& fibers,
        const std::unordered_multimap<PortKey, int32_t, PortKeyHash>& by_port)
        : fiber_by_id_(fibers), fiber_by_port_(by_port) {}
    
    // ═══ 解析一条连纤的完整拓扑信息 ═══
    std::optional<FiberTopologyInfo> resolve(int32_t fiber_id) const {
        auto it = fiber_by_id_.find(fiber_id);
        if (it == fiber_by_id_.end()) return std::nullopt;
        
        const auto& fiber = it->second;
        if (!fiber.is_inter_ne) return std::nullopt;
        
        FiberTopologyInfo info;
        info.fiber_id = fiber_id;
        
        // 源端
        info.src_board_id   = fiber.src_board_id;
        info.src_port_id    = fiber.src_port_id;
        info.src_board_type = fiber.src_board_type;
        
        // 宿端
        info.dst_board_id   = fiber.dst_board_id;
        info.dst_port_id    = fiber.dst_port_id;
        info.dst_board_type = fiber.dst_board_type;
        
        // 场景判断
        if (fiber.dst_board_type == BoardType::ACTIVE) {
            info.scene_type    = 1;
            info.scenario_case = 0;
        } else {
            info.scene_type = 2;
            
            auto peer2 = find_intra_ne_peer(fiber.dst_board_id, 2);
            if (peer2) {
                info.dst_peer_boards.push_back({*peer2, 2});
            }
            
            auto peer3 = find_intra_ne_peer(fiber.dst_board_id, 3);
            if (peer3) {
                info.dst_peer_boards.push_back({*peer3, 3});
            }
            
            bool has2 = std::any_of(info.dst_peer_boards.begin(),
                                   info.dst_peer_boards.end(),
                                   [](const auto& p){ return p.via_port == 2; });
            bool has3 = std::any_of(info.dst_peer_boards.begin(),
                                   info.dst_peer_boards.end(),
                                   [](const auto& p){ return p.via_port == 3; });
            
            info.scenario_case = (has2 && has3) ? 1   // Case A
                               : (has2)         ? 2   // Case B
                               :                  3;  // Case C
        }
        
        return info;
    }
    
    // ═══ 批量解析 ═══
    std::unordered_map<int32_t, FiberTopologyInfo>
    resolve_batch(const std::vector<int32_t>& fiber_ids) const {
        std::unordered_map<int32_t, FiberTopologyInfo> results;
        results.reserve(fiber_ids.size());
        for (int32_t id : fiber_ids) {
            auto info = resolve(id);
            if (info) results[id] = std::move(*info);
        }
        return results;
    }

private:
    std::optional<int32_t> find_intra_ne_peer(
        int32_t board_id, int8_t port_id) const 
    {
        auto range = fiber_by_port_.equal_range({board_id, port_id});
        for (auto it = range.first; it != range.second; ++it) {
            const auto& fiber = fiber_by_id_.at(it->second);
            if (!fiber.is_inter_ne) {
                return (fiber.src_board_id == board_id) 
                    ? fiber.dst_board_id : fiber.src_board_id;
            }
        }
        return std::nullopt;
    }
};
```

```cpp
class ScenarioRegistry {
    std::vector<std::unique_ptr<IColorStrategy>> strategies_;
    
public:
    void register_strategy(std::unique_ptr<IColorStrategy> strategy) {
```

```cpp
class PerfQueryHelper {
    const FiberTopologyResolver& resolver_;
    
public:
    // 构造性能 RPC 请求
    PerformanceRequest build_request(
        const std::vector<PerfTargetBuilder::PerfQueryTarget>& targets) const {
        PerformanceRequest req;
        for (const auto& t : targets) {
            auto* target = req.add_targets();
            target->set_board_id(t.board_id);
            target->set_port_id(t.port_id);
        }
        return req;
    }
    
    // 构造衰耗 RPC 请求（去重）
    PerformanceRequest build_spanloss_request(
        const std::vector<SpanlossTargetBuilder::SpanlossPair>& pairs) const {
        std::set<PortKey> unique;
        for (const auto& p : pairs) {
            unique.insert({p.src_board_id, p.src_port_id});
            unique.insert({p.dst_board_id, p.dst_port_id});
        }
        PerformanceRequest req;
        for (const auto& [bid, pid] : unique) {
            auto* target = req.add_targets();
            target->set_board_id(bid);
            target->set_port_id(pid);
        }
        return req;
    }
    
    // 在响应中查找性能值
    double find_value(const PerformanceResponse& resp,
                      int32_t board_id, int8_t port_id,
                      PerfMetric metric) const {
        for (const auto& perf : resp.performances()) {
            if (perf.board_id() == board_id && perf.port_id() == port_id) {
                return (metric == OOP) ? perf.oop() : perf.iop();
            }
        }
        return 0.0;
    }
};
```

## 11. 线程模型

### 11.1 线程清单

| 线程                  | 数量     | 职责                                                  | 生命周期       |
| --------------------- | -------- | ----------------------------------------------------- | -------------- |
| gRPC Server 线程池    | gRPC管理 | 处理 RPC 请求（GetFiberColor、GetFiberPerformance等） | 服务全生命周期 |
| alarm_stream_thread_  | 1        | 订阅告警事件流，写入合并队列                          | 断线自动重连   |
| fiber_stream_thread_  | 1        | 订阅拓扑事件流，写入有序队列                          | 断线自动重连   |
| event_process_thread_ | 1        | 串行消费所有事件，计算颜色                            | 服务全生命周期 |
| output_thread_        | 1        | 批量DB写入 + 颜色事件推送                             | 服务全生命周期 |
| timer_thread_         | 1        | 趋势采集 + 数据清理                                   | 服务全生命周期 |

### 11.2 线程间通信

```
alarm_stream_thread_ ──┐
                       ├──→ CoalescingEventQueue ──→ event_process_thread_
fiber_stream_thread_ ──┘                                    │
                                                            │ change_queue (SPSC)
                                                            ▼
                                                     output_thread_

gRPC 线程池 ──→ FiberTopologyResolver（只读，无锁）──→ PerfService RPC
              （性能查询接口，与事件处理线程无共享写状态）

timer_thread_ ──→ DB（独立）
```

### 11.3 同步机制

| 通信路径              | 机制                                | 说明                 |
| --------------------- | ----------------------------------- | -------------------- |
| Stream → EventQueue   | `std::mutex` + `condition_variable` | 有界队列             |
| EventQueue → 处理线程 | `condition_variable`                | 超时100ms            |
| 处理线程 → 输出线程   | SPSC 无锁环形队列                   | 单生产者单消费者     |
| 处理线程内部          | **无锁**                            | 所有缓存仅该线程访问 |
| gRPC 线程 → 拓扑数据  | 只读访问（COW 或 RCU）              | 无写冲突             |

### 11.4 关键设计：单线程消费消除竞态

```
event_process_thread_ 独占写访问：
  · alarm_cache_
  · fiber_by_id_ / fiber_by_port_
  · port_dependency_index_
  · color_contexts_

gRPC 线程只读访问（通过快照或读写锁）：
  · FiberTopologyResolver::resolve()（性能查询用）
  · GetColoredFibers()（颜色查询用）

→ 写端无锁，读端通过快照隔离
```

### 12.1 CoalescingEventQueue

```cpp
class CoalescingEventQueue {
public:
    struct EventBatch {
        std::vector<AlarmEvent> alarms;   // 已合并，每个key仅最新一条
        std::vector<FiberEvent> fibers;   // 有序，未合并
    };

private:
    // 告警合并区
    std::unordered_map<AlarmCacheKey, AlarmEvent, AlarmCacheKeyHash> alarm_pending_;
    mutable std::mutex alarm_mutex_;
    
    // 连纤有序队列
    std::queue<FiberEvent> fiber_queue_;
    mutable std::mutex fiber_mutex_;
    
    // 通知
    std::mutex notify_mutex_;
    std::condition_variable notify_cv_;
    std::atomic<bool> has_data_{false};
    
    static constexpr size_t MAX_ALARM_PENDING = 10000;
    static constexpr size_t MAX_FIBER_QUEUE   = 1000;

public:
    void push_alarm(const AlarmEvent& event) {
        AlarmCacheKey key{event.board_id(), event.port_id(), event.alarm_level()};
        {
            std::lock_guard<std::mutex> lock(alarm_mutex_);
            alarm_pending_[key] = event;  // 覆盖式，保留最新
        }
        signal();
    }
    
    void push_fiber(const FiberEvent& event) {
        {
            std::lock_guard<std::mutex> lock(fiber_mutex_);
            fiber_queue_.push(event);
        }
        signal();
    }
    
    EventBatch drain() {
        EventBatch batch;
        {
            std::lock_guard<std::mutex> lock(alarm_mutex_);
            batch.alarms.reserve(alarm_pending_.size());
            for (auto& [key, event] : alarm_pending_) {
                batch.alarms.push_back(std::move(event));
            }
            alarm_pending_.clear();
        }
        {
            std::lock_guard<std::mutex> lock(fiber_mutex_);
            batch.fibers.reserve(fiber_queue_.size());
            while (!fiber_queue_.empty()) {
                batch.fibers.push_back(std::move(fiber_queue_.front()));
                fiber_queue_.pop();
            }
        }
        has_data_.store(false, std::memory_order_release);
        return batch;
    }
    
    bool wait_for_data(int timeout_ms = 100) {
        if (has_data_.load(std::memory_order_acquire)) return true;
        std::unique_lock<std::mutex> lock(notify_mutex_);
        return notify_cv_.wait_for(lock, std::chrono::milliseconds(timeout_ms),
            [this]{ return has_data_.load(std::memory_order_acquire); });
    }

private:
    void signal() {
        has_data_.store(true, std::memory_order_release);
        notify_cv_.notify_one();
    }
};
```

### 12.2 合并语义

| 场景                     | 原始事件 | 合并后 | 减少          |
| ------------------------ | -------- | ------ | ------------- |

| 轻度闪断（1s内5次翻转）  | 5        | 1      | 80%           |

| ----------------------------- | -------------------------------------- |

```cpp
void FiberMaintServiceImpl::event_processing_loop() {
    while (running_.load(std::memory_order_acquire)) {
        event_queue_.wait_for_data(100);
        auto batch = event_queue_.drain();
        
        if (batch.fibers.empty() && batch.alarms.empty()) continue;
        
        // Phase 1: 连纤事件（更新拓扑 + 依赖索引）
        for (const auto& fiber_event : batch.fibers) {
            handle_fiber_event(fiber_event);
        }
        
        // Phase 2: 告警事件（更新缓存 + 触发重算）
        for (const auto& alarm_event : batch.alarms) {
            handle_alarm_event(alarm_event);
        }
    }
}
```

```cpp
void FiberMaintServiceImpl::handle_alarm_event(const AlarmEvent& event) {
    AlarmCacheKey cache_key{event.board_id(), event.port_id(), event.alarm_level()};
    
    // Step 1: 更新缓存（R-25: 先更新）
    if (event.type() == ALARM_RAISED) {
        alarm_cache_[cache_key] = {event.timestamp_ms()};
    } else {
        alarm_cache_.erase(cache_key);
    }
    
    // Step 2: O(1) 查找受影响连纤
    PortKey port_key{event.board_id(), event.port_id()};
    auto it = port_dependency_index_.find(port_key);
    if (it == port_dependency_index_.end()) return;
    
    // Step 3: 重算颜色
    for (const auto& dep : it->second) {
        recalculate_fiber_color(dep.fiber_id, dep.role, event);
    }
}
```

```cpp
void FiberMaintServiceImpl::recalculate_fiber_color(
    int32_t fiber_id, int8_t role, const AlarmEvent& trigger_event) 
{
    auto ctx_it = color_contexts_.find(fiber_id);
    if (ctx_it == color_contexts_.end()) return;
    auto& ctx = ctx_it->second;
    
    // 获取策略
    auto topo_info = topo_resolver_.resolve(fiber_id);
    if (!topo_info) return;
    const auto* strategy = scenario_registry_.match(*topo_info);
    if (!strategy) return;
    
    // 短路预判
    if (strategy->can_skip(ctx, trigger_event)) return;
    
    // 计算（纯内存，R-24）
    FiberColor new_color = strategy->evaluate(ctx, alarm_cache_);
    
    // 比较
    if (new_color == ctx.current_color) return;
    
    // 变化 → 推入输出队列
    FiberColor old_color = ctx.current_color;
    ctx.current_color = new_color;
    ctx.last_change_ms = current_time_ms();
    
    change_queue_.push(ColorChangeRecord{
        fiber_id, old_color, new_color,
        strategy->scene_type(), strategy->scenario_case(),
        ctx.last_change_ms
    });
}
```

### 14.2 通用依赖构建器

```cpp
class DependencyBuilder {
    std::unordered_map<PortKey, std::vector<DependencyEntry>, PortKeyHash>& index_;
    const ScenarioRegistry& registry_;
    const FiberTopologyResolver& resolver_;
    
public:
    void build(const FiberCacheEntry& fiber) {
        auto topo_info = resolver_.resolve(fiber.fiber_id);
        if (!topo_info) return;
        
        const auto* strategy = registry_.match(*topo_info);
        if (!strategy) return;
        
        auto deps = strategy->declare_alarm_dependencies(*topo_info);
        for (const auto& dep : deps) {
            PortKey key{dep.board_id, dep.port_id};
            index_[key].push_back({fiber.fiber_id, dep.role});
        }
    }
    
    void remove(int32_t fiber_id) {
        for (auto it = index_.begin(); it != index_.end(); ) {
            auto& entries = it->second;
            entries.erase(
                std::remove_if(entries.begin(), entries.end(),
                    [fiber_id](const DependencyEntry& e) { 
                        return e.fiber_id == fiber_id; }),
                entries.end());
            if (entries.empty()) it = index_.erase(it);
            else ++it;
        }
    }
    
    void rebuild(const FiberCacheEntry& fiber) {
        remove(fiber.fiber_id);
        build(fiber);
    }
    
    void build_all(const std::unordered_map<int32_t, FiberCacheEntry>& fibers) {
        index_.clear();
        for (const auto& [id, fiber] : fibers) {
            if (fiber.is_inter_ne) build(fiber);
        }
    }
};
```

### 14.3 索引维护时机

| 事件                    | 操作                            |

## 16. 异步输出层

### 16.1 SPSC 无锁队列

```cpp
template<typename T, size_t Capacity = 4096>
class SPSCQueue {
    alignas(64) std::atomic<size_t> write_pos_{0};
    alignas(64) std::atomic<size_t> read_pos_{0};
    std::array<T, Capacity> buffer_;
    
public:
    bool push(const T& item) {
        size_t wp = write_pos_.load(std::memory_order_relaxed);
        size_t next = (wp + 1) % Capacity;
        if (next == read_pos_.load(std::memory_order_acquire)) return false;
        buffer_[wp] = item;
        write_pos_.store(next, std::memory_order_release);
        return true;
    }
    
    bool pop(T& item) {
        size_t rp = read_pos_.load(std::memory_order_relaxed);
        if (rp == write_pos_.load(std::memory_order_acquire)) return false;
        item = buffer_[rp];
        read_pos_.store((rp + 1) % Capacity, std::memory_order_release);
        return true;
    }
};
```

```cpp
    batch.reserve(64);

        std::this_thread::sleep_for(std::chrono::milliseconds(10));

            batch.push_back(record);

        batch_upsert_fiber_colors(batch);
        batch_insert_color_changes(batch);
        
        // 推送
        notify_color_subscribers(batch);
        
        batch.clear();
```

### 16.3 同 Fiber 去重

```cpp
void deduplicate_batch(std::vector<ColorChangeRecord>& batch) {
    // GREEN→YELLOW→RED 合并为 GREEN→RED
    std::unordered_map<int32_t, size_t> first_occurrence;
    std::vector<ColorChangeRecord> deduped;
    
    for (auto& r : batch) {
        auto it = first_occurrence.find(r.fiber_id);
        if (it == first_occurrence.end()) {
            first_occurrence[r.fiber_id] = deduped.size();
            deduped.push_back(r);
        } else {
            deduped[it->second].new_color = r.new_color;
            deduped[it->second].timestamp_ms = r.timestamp_ms;
        }
    }
    
    // 移除 old == new 的无效记录
    deduped.erase(
        std::remove_if(deduped.begin(), deduped.end(),
            [](const auto& r) { return r.old_color == r.new_color; }),
        deduped.end());
    
    batch = std::move(deduped);
}
```

### 18.2 FlapDetector（第二阶段可选）

```cpp
class FlapDetector {
    struct FlapState {
        int64_t window_start_ms = 0;
        uint16_t flip_count = 0;
        bool suppressed = false;
        int64_t suppress_until_ms = 0;
    };
    
    std::unordered_map<AlarmCacheKey, FlapState, AlarmCacheKeyHash> states_;
    static constexpr uint16_t THRESHOLD = 10;
    static constexpr int64_t  SUPPRESS_MS = 2000;
    
public:
    bool should_suppress(const AlarmCacheKey& key, int64_t now_ms) {
        auto& s = states_[key];
        if (now_ms - s.window_start_ms > 1000) {
            s.window_start_ms = now_ms;
            s.flip_count = 0;
        }
        s.flip_count++;
        
        if (s.flip_count > THRESHOLD && !s.suppressed) {
            s.suppressed = true;
            s.suppress_until_ms = now_ms + SUPPRESS_MS;
            return true;
        }
        if (s.suppressed) {
            if (now_ms >= s.suppress_until_ms) {
                s.suppressed = false;
                s.flip_count = 0;
                return false;
            }
            return true;
        }
        return false;
    }
};
```

```cpp
    EXPECT_TRUE(summary.has_critical);
    EXPECT_TRUE(summary.has_minor);
}

// ═══ 合并队列 ═══
TEST(CoalescingQueue, SameKey_Merge) {
    queue.push_alarm(raised_event);
    queue.push_alarm(cleared_event);
    auto batch = queue.drain();
    EXPECT_EQ(batch.alarms.size(), 1);
    EXPECT_EQ(batch.alarms[0].type(), ALARM_CLEARED);
}

TEST(CoalescingQueue, DifferentLevel_NoMerge) {
```

### 24.3 关键设计决策记录

| 决策             | 选项                  | 选择           | 理由             |
| ---------------- | --------------------- | -------------- | ---------------- |
| 事件消费模型     | 多线程+锁 / 单线程    | **单线程**     | 消除竞态         |
| 告警缓存模型     | 计数器 / 存在性       | **存在性**     | R-26/R-27        |
| 依赖索引 Key     | 含 alarm_level / 不含 | **不含**       | 任何级别都需重算 |
| FIBER_CREATED    | RPC / 事件携带        | **事件携带**   | 消除阻塞         |
| 闪断处理         | 消费侧 / 入队侧       | **入队侧为主** | 更简单有效       |
| 场景扩展         | 修改核心 / 策略模式   | **策略模式**   | 开闭原则         |
| 依赖构建         | 硬编码 / 自声明       | **自声明**     | 零硬编码         |
| DB 写入          | 同步 / 异步           | **异步批量**   | 不阻塞           |
| 队列满           | 丢弃 / 阻塞           | **阻塞**       | NF-17            |
| 拓扑解析与业务   | 合并 / 分层           | **分层**       | 低耦合           |
| 性能查询场景判断 | 6处重复 / 共享Layer1  | **共享**       | DRY              |
| 告警与性能目标   | 统一Builder / 分离    | **分离**       | 查询范围不同     |

### 24.4 术语表

| 术语                        | 说明                               |
| --------------------------- | ---------------------------------- |
| 网元间连纤 (Inter-NE Fiber) | 连接不同网元的物理光纤             |
| 网元内连纤 (Intra-NE Fiber) | 同一网元内板卡间的跳纤             |
| 有源盘 (Active Board)       | 需要供电的板卡（OTU、线路板等）    |
| 无源盘 (Passive Board)      | 无需供电的板卡（OMU、ODU等）       |
| OOP                         | 输出光功率 (Output Optical Power)  |
| IOP                         | 输入光功率 (Input Optical Power)   |
| 跨段损耗 (Spanloss)         | 光纤段的光功率衰减 = 源OOP - 宿IOP |
| 闪断 (Flap)                 | 告警在短时间内频繁产生/清除        |
| 保护倒换                    | 主路故障时业务切换到备路           |
