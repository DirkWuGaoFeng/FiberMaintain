# 光纤维护服务系统 Agent 优化设计方案 v3\.1

> **基于 v3\.0 最终版 \+ 正式接口文档 \+ 需求确认意见 优化落地**
> **适配场景**：个人本地项目 / 单用户 / 生产级稳定性 / 扩展能力预留
> 
> 

---

## 一、优化说明与核心原则

### 1\.1 优化背景

本方案在原 v3\.0 需求规格说明书基础上，结合正式接口文档、7 项需求确认意见，以及工业级 Agent 最佳实践进行迭代，核心方向是**职责收口、架构精简、接口对齐、能力预留**，形成可直接进入编码阶段的落地方案。

### 1\.2 核心优化点总览

|优化项|原方案|优化后方案|
|---|---|---|
|Sub\-Agent 实例化|粒度模糊，批量易产生大量实例|「常驻注册 \+ 按需实例化 \+ 批量单实例处理」，明确并发模型|
|拓扑分析职责|含场景识别逻辑|移除场景识别，纯拓扑数据查询，场景信息完全由后端返回|
|实时统计链路|Agent 层参与统计推送|Agent 层完全不参与，前端直连后端 WebSocket|
|工具权限|多 Agent 重叠持有数据查询工具|数据查询统一收口到 data\-collector，职责隔离|
|沙箱设计|移除沙箱|保留 Docker 沙箱能力作为扩展预留，当前版本不启用|
|RAG 初始化|仅定义分类，无落地内容|提供 6 大类 16 篇 Mock 文档模板，支持一键初始化|
|rag\-retriever|独立 Sub\-Agent|降级为工具集，通用知识由中间件注入，减少调度开销|
|接口对齐|部分工具与接口不匹配|100% 对齐正式 REST/gRPC 接口，修正工具定义|

### 1\.3 不变的核心设计基石

严格坚守「**Agent 不做业务计算**」第一原则：衰耗计算、颜色判定、场景识别 100% 由 C\+\+ 后端确定性系统完成，Agent 仅负责意图理解、任务编排、结果解读与报告生成。

### 2\.2 关键架构变更说明

1. **移除独立统计推送服务**：Vue3 统计面板直接连接后端 `:8081` WebSocket，Agent 层完全不参与实时数据链路，降低复杂度与故障点。

2. **精简 Sub\-Agent 数量**：移除独立的 `rag-retriever` Sub\-Agent，知识检索能力下沉为中间件 \+ 工具集，减少一层调度开销。

3. **沙箱能力预留**：保留 Docker Sandbox 运行环境与工具入口，默认关闭，为后续自定义计算、仿真分析等扩展场景预留。

## 三、Agent 层核心设计（重点优化）

### 3\.1 Sub\-Agent 实例化模型（优化落地方案）

采用 **「角色定义常驻 \+ 执行实例按需创建 \+ 批量单实例处理」** 三级模型，彻底解决原方案粒度模糊、并发不可控的问题。

#### 3\.1\.1 模型详细定义

1. **注册层：5 类角色静态常驻**

    - 5 类 Sub\-Agent 以角色配置的形式在 DeerFlow 中预先注册，定义 System Prompt、绑定工具集、模型参数

    - 常驻的是元数据定义，而非运行进程，无持续资源占用

2. **执行层：任务级临时实例**

    - Lead Agent 每次调用 `task` tool 时，动态创建对应类型的执行实例，任务完成后立即销毁

    - 实例间完全隔离，无状态共享，避免上下文污染

3. **批量场景：单实例批量处理**

    - 批量分析任务仅创建 1 个 `data-collector` 实例调用批量接口拉取全量数据，再创建 1 个 `analysis-expert` 实例集中解读

    - **禁止为每条光纤单独创建 Sub\-Agent 实例**，从根源控制调度开销与后端压力

#### 3\.1\.2 并发控制规则（优化后）

|参数|优化后值|说明|
|---|---|---|
|全局最大并发实例数|5|同时运行的 Sub\-Agent 执行实例不超过 5 个|
|单批量任务占用并发|≤2|1 个数据采集 \+ 1 个分析，不额外占用|
|排队策略|FIFO|超出并发数进入队列等待|
|单任务超时|15s|单个 Sub\-Agent 实例执行超时|
|批量总超时|30s|整批任务超时阈值|
|后端主动限流|5xx 错误率 \> 10% 时，并发降至 2|MCP 连接器滑动窗口统计，自动降载保护后端|

### 3\.2 优化后 Sub\-Agent 职责与权限

#### 3\.2\.1 Lead Agent（主智能体）

|属性|值|
|---|---|
|模型|qwen3\.6 primary 模式|
|最大迭代|10 轮|
|核心职责|意图识别、任务分解、Sub\-Agent 派遣、结果汇总、异常兜底、多轮对话|
|核心约束|不直接调用业务工具、不做业务计算；离线模式下仅放行知识类意图|

#### 3\.2\.2 topology\-analyst（拓扑分析师）

**职责调整：移除场景识别，纯拓扑数据查询**

|属性|值|
|---|---|
|模型|qwen3\.6 fast 模式|
|核心职责|查询连纤连接信息、单盘信息、网元下设备列表|
|移除职责|场景类型判定、端口状态逻辑判断（完全由后端负责）|
|绑定工具|`fiber_connection_query`、`batch_fiber_connection_query`、`board_query`、`batch_board_query`|

#### 3\.2\.3 data\-collector（数据采集师）

**职责强化：统一收口所有业务数据查询**

|属性|值|
|---|---|
|模型|qwen3\.6 fast 模式|
|核心职责|所有光纤性能、衰耗、告警、颜色列表、统计、趋势数据的查询获取|
|权限原则|原始业务数据 100% 由本 Agent 提供，其他 Sub\-Agent 不直接调用后端数据接口|
|绑定工具|10 个业务数据类工具（详见第四章）|

#### 3\.2\.4 analysis\-expert（分析专家）

**职责调整：仅结果解读 \+ 对比分析，预留沙箱能力**

|属性|值|
|---|---|
|模型|qwen3\.6 primary 模式|
|核心职责|解读后端返回结果、异常检测、纵向 / 横向对比分析、生成分析结论|
|数据来源|全部由 data\-collector 传入，不直接调用后端数据接口|
|预留能力|Docker 沙箱脚本执行（默认关闭）|
|绑定工具|`memory_query`、`memory_save`、`sandbox_exec`（预留）|

#### 3\.2\.5 report\-generator（报告生成师）

|属性|值|
|---|---|
|模型|qwen3\.6 primary 模式|
|核心职责|生成结构化分析报告、维护建议、多格式文件导出|
|绑定工具|`rag_query`、`export_pdf`、`export_excel`、`export_csv`|

## 四、Tools 工具体系设计（100% 对齐正式接口）

### 4\.1 设计原则

1. 严格对齐后端 REST API，一个 Tool 对应一个接口，不做业务封装

2. 权限分层：数据类工具仅 `data-collector` 持有，分析类工具仅 `analysis-expert` 持有

3. 优先使用批量接口，减少 HTTP 请求数，降低后端压力

### 4\.2 工具总清单（共 18 个，分 4 类）

#### 拓扑类（4 个，仅 topology\-analyst）

|Tool 名称|对应后端 API|说明|
|---|---|---|
|`fiber_connection_query`|`GET /api/v1/topology/fibers/{fiber_id}`|单条连纤信息查询|
|`batch_fiber_connection_query`|`POST /api/v1/topology/fibers/batch`|批量连纤查询（≤200 条）|
|`board_query`|`GET /api/v1/boards/{board_id}`|单盘查询（含端口、所属 ne\_id）|
|`batch_board_query`|`POST /api/v1/boards/batch`|批量单盘查询（≤200 条）|

> **说明**：移除原方案 `ne_query` 工具，网元维度查询通过批量单盘接口按 `ne_id` 筛选实现，完全对齐现有接口。
> 
> 

#### 业务数据类（10 个，仅 data\-collector）

|Tool 名称|对应后端 API|说明|
|---|---|---|
|`fiber_performance_query`|`GET /api/v1/fibers/{fiber_id}/performance`|单条光纤性能（OOP/IOP）|
|`batch_fiber_performance_query`|`BatchGetFiberPerformance` \(gRPC/REST\)|批量光纤性能（≤200 条）|
|`fiber_spanloss_query`|`GET /api/v1/fibers/{fiber_id}/spanloss`|单条光纤衰耗值|
|`batch_fiber_spanloss_query`|`BatchGetFiberSpanloss` \(gRPC/REST\)|批量光纤衰耗（≤200 条）|
|`alarm_query`|`GET /api/v1/alarms/current`|单端口当前告警|
|`batch_alarm_query`|`BatchGetCurrentAlarms` \(gRPC/REST\)|批量端口告警（≤50 条）|
|`colored_fibers_query`|`GET /api/v1/fibers/colored`|按颜色筛选有颜色连纤|
|`all_colored_fibers_query`|`GET /api/v1/fibers/colored/all`|获取全部有颜色连纤|
|`fiber_stats_query`|`GET /api/v1/fibers/stats/realtime`|实时统计数据|
|`fiber_trend_query`|`GET /api/v1/fibers/stats/trend`|趋势数据查询（支持时间范围）|

#### 知识与导出类（3 个）

|Tool 名称|所属 Agent|说明|
|---|---|---|
|`rag_query`|report\-generator / analysis\-expert|RAG 知识库精准检索|
|`knowledge_upload`|管理员工具|知识库文档上传入库|
|`export_pdf` / `export_excel` / `export_csv`|report\-generator|报告文件导出|

#### 扩展预留类（1 个，默认禁用）

|Tool 名称|所属 Agent|说明|
|---|---|---|
|`sandbox_exec`|analysis\-expert|Docker 沙箱脚本执行；当前版本关闭，后续自定义计算场景启用|

### 4\.3 MCP 连接器优化

- **超时对齐**：单条接口 2s 超时，批量接口 5s 超时，严格匹配接口文档约定

- **重试策略**：5xx 错误最多重试 2 次，4xx 错误不重试

- **错误映射**：将 HTTP 错误码映射为业务错误类型（NOT\_FOUND / PORT\_OCCUPIED / BATCH\_LIMIT\_EXCEEDED 等），便于 Agent 精准处理

- **负载感知**：滑动窗口统计 1 分钟内 5xx 错误率，超过 10% 自动触发 Agent 层降并发

- **全量审计**：每次调用记录 method、path、status、耗时、trace\_id，统一输出审计日志

## 五、Middleware 中间件体系优化

保留 4 个核心中间件，优化内部逻辑，提升稳定性与精准度。

### 5\.1 ModelDegradationMiddleware（模型降级）

- **降级链路**：qwen3\.6 primary → 简化版 primary → fast 模型 → 熔断

- **新增健康检测**：定期探活 OLLAMA 服务，故障时提前触发降级，无需等待超时

- **新增纯规则兜底**：OLLAMA 完全不可用时，高频查询场景切换为固定 Markdown 模板输出，直接调用后端 API 返回结构化数据，保障核心功能可用

- **熔断器**：连续 3 次失败触发熔断，60s 后半开恢复

### 5\.2 FiberDomainValidationMiddleware（领域校验）

- **触发时机**：data\-collector 获取数据后，传入 analysis\-expert 之前执行

- **校验规则**：

    - 网元间连纤校验：`src_ne_id ≠ dst_ne_id`

    - 光功率范围：OOP \-30\\\+10 dBm，IOP \-40\\\+5 dBm

    - 衰耗范围：0\~30 dB

- **处理方式**：异常数据标记后传递，不丢弃，由 analysis\-expert 在结论中明确标注异常

### 5\.3 RAGInjectionMiddleware（知识注入）

- **升级注入策略**：从「单关键词命中」升级为「意图分类 \+ 多知识库组合注入」，先识别用户意图大类，再注入对应组合的知识片段

- **优化匹配规则**：增加否定词过滤，降低误触发；注入前经过 Reranker 精排，仅保留 Top\-3 高相关片段

- **注入上限**：总 token 数 ≤ 2000，避免上下文膨胀

### 5\.4 AuditLogMiddleware（审计日志）

- **记录内容**：trace\_id、工具名称、入参、状态、耗时、时间戳

- **输出格式**：JSON Lines 格式，本地文件存储

- **会话关联**：通过 trace\_id 串联同一会话的所有工具调用，便于问题排查

- **保留周期**：审计日志保留 90 天，运行日志保留 30 天

## 六、Markdown Skills 技能体系

保留 5 大核心技能，调整执行步骤对齐新的职责划分，所有技能严格遵循「数据采集 → 校验 → 分析 → 输出」的标准化流程。

### 6\.1 fiber\_spanloss\_analysis（衰耗分析技能）

**执行流程**：

1. data\-collector 调用批量接口获取光纤性能 \+ 衰耗数据

2. 领域校验中间件校验数据合理性

3. 匹配 RAG 阈值标准作为参考

4. analysis\-expert 基于后端结果生成状态判定与结论

5. 输出标准化 Markdown 表格

### 6\.2 fiber\_color\_diagnosis（颜色诊断技能）

**执行流程**：

1. data\-collector 获取颜色列表、关联告警、性能数据

2. 后端已返回 `scene_type` 和 `scenario_case`，Agent 直接展示，不做场景判定

3. 按 P0\~P3 优先级排序，生成处理建议

4. 引用 RAG 告警处理指南补充规范依据

### 6\.3 batch\_fiber\_analysis（批量分析技能）

**执行流程（优化后）**：

1. data\-collector 调用批量接口一次性拉取所有目标光纤数据

2. analysis\-expert 单实例批量解读，按严重程度排序

3. 归纳共性问题，生成优先处理清单

4. 输出汇总报告 \+ 成功 / 失败统计

### 6\.4 fiber\_trend\_analysis（趋势分析技能）

**执行流程**：

1. data\-collector 获取指定时间范围的趋势数据 \+ 实时统计

2. analysis\-expert 识别异常突增、周期波动、持续劣化等特征

3. 结合长期记忆做同比 / 环比对比

4. 生成趋势结论与维护建议

### 6\.5 ne\_health\_check（网元巡检技能）

**执行流程**：

1. topology\-analyst 获取网元下所有单盘与关联连纤

2. data\-collector 批量拉取所有连纤的性能、衰耗、告警、颜色数据

3. analysis\-expert 逐条检查，计算健康评分

4. 输出巡检报告与问题清单

## 七、RAG 知识库系统与 Mock 初始化方案

### 7\.1 技术配置保持不变

- 向量数据库：ChromaDB

- Embedding：BAAI/bge\-large\-zh\-v1\.5

- 检索策略：Vector \(0\.6\) \+ BM25 \(0\.4\) → Reranker → Top\-3

- 分块策略：512 tokens，重叠 50 tokens

### 7\.2 Mock 文档初始化方案

提供 6 大类共 16 篇初始文档的标准 Markdown 模板，项目启动时可一键导入 ChromaDB，快速构建可用的基础知识库。

#### 01\_设备技术手册（3 篇）

1. `有源盘技术规格.md`：包含盘类型、端口数、光功率量程、典型应用场景、使用约束

2. `无源盘技术规格.md`：3 端口定义、用途约束、无源光学特性、插损指标

3. `端口规格与约束.md`：端口占用规则、用途匹配规则、级联删除逻辑
