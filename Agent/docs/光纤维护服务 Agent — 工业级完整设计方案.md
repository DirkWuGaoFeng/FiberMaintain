> **版本**：v6.0-Industrial | **定位**：电信级生产系统 | **基线**：接口文档 v2.3 + v5.1 评估结论

## 第一部分：设计哲学与顶层决策

### 1.1 核心命题（修订）

v5.1 的命题是"LLM 不可信，用工程手段约束它"。这正确但不完整。

**v6.0 命题：**

> **LLM 是系统的"认知接口层"，不是"决策层"。系统的确定性由规则引擎和后端计算保证；LLM 的价值在于将运维人员的自然语言意图无损翻译为系统可执行的结构化指令，并将系统返回的结构化数据翻译为人类可理解的运维语言。**

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   运维人员（人）                                                 │
│       │                                                         │
│       │  自然语言（模糊、省略、口语化）                           │
│       ▼                                                         │
│   ┌─────────────────────────────────┐                           │
│   │  认知接口层（LLM）              │  ← 唯一职责：翻译          │
│   │  • 意图识别                     │                           │
│   │  • 参数提取                     │                           │
│   │  • 结果表述                     │                           │
│   └─────────────────────────────────┘                           │
│       │                                                         │
│       │  结构化指令（精确、类型化、可校验）                       │
│       ▼                                                         │
│   ┌─────────────────────────────────┐                           │
│   │  确定性执行层（规则 + 后端）     │  ← 唯一职责：执行          │
│   │  • 参数校验                     │                           │
│   │  • API 调用                     │                           │
│   │  • 阈值判断                     │                           │
│   │  • 统计计算                     │                           │
│   └─────────────────────────────────┘                           │
│       │                                                         │
│       │  结构化数据                                              │
│       ▼                                                         │
│   ┌─────────────────────────────────┐                           │
│   │  认知接口层（LLM）              │  ← 唯一职责：表述          │
│   │  • 数据解读                     │                           │
│   │  • 报告生成                     │                           │
│   │  • 建议组织                     │                           │
│   └─────────────────────────────────┘                           │
│       │                                                         │
│       │  自然语言（清晰、专业、可操作）                           │
│       ▼                                                         │
│   运维人员（人）                                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**设计理由：** 将 LLM 的职责严格限定为"翻译"，意味着：

- LLM 出错 → 翻译错误 → 被校验层拦截 → 追问用户（可控）
- LLM 不可用 → 翻译层失效 → 规则引擎兜底（降级但可用）
- LLM 幻觉 → 编造数据 → 但数据全部来自后端（不可能编造）

### 1.2 八条设计原则

| #    | 原则         | 一句话解释                               | 工业依据                |
| ---- | ------------ | ---------------------------------------- | ----------------------- |
| P1   | LLM 只做翻译 | 不计算、不判断、不决策                   | YD/T 3252 计算可追溯性  |
| P2   | 单一数据出口 | 仅一个组件可调用后端 API                 | 最小权限原则 / 审计收敛 |
| P3   | 确定性分层   | 规则引擎处理确定性请求，LLM 处理模糊请求 | 电信 <2s 响应要求       |
| P4   | 参数不可信   | LLM 提取的参数必须经过校验才能到达 API   | 防误操作                |
| P5   | 四级+降级    | 从规则兜底到纯文本，系统永远有输出       | 99.99% 可用性           |
| P6   | 全链路审计   | 每次交互可追溯到"谁、何时、做了什么"     | 电信合规 / 等保三级     |
| P7   | 离线可降级   | 网络中断时核心功能仍可用                 | 机房断网场景            |
| P8   | 可观测优先   | 每个节点的输入/输出/耗时/状态均可追踪    | 故障定位 <5min          |

### 1.3 与 v5.1 的关键差异

| 维度     | v5.1                   | v6.0                             | 变更理由               |
| -------- | ---------------------- | -------------------------------- | ---------------------- |
| 请求入口 | 全部走 LLM             | **L0 规则引擎前置**              | 80% 请求可 <500ms 响应 |
| LLM 定位 | 意图识别 + 分析 + 报告 | **仅翻译（入/出）**              | 减少 LLM 出错面        |
| 参数校验 | 五层                   | **三层 + 两道断言**              | 去除冗余，降低维护成本 |
| 实时能力 | 无                     | **WebSocket 事件驱动**           | 主动运维刚需           |
| 审计     | 无                     | **全链路操作审计**               | 等保三级合规           |
| 离线     | 无                     | **本地缓存 + 规则降级**          | 机房断网场景           |
| 响应时间 | 无约束                 | **分级 SLA（<1s / <3s / <10s）** | 运维体验               |
| 主动巡检 | 无                     | **定时 + 事件触发**              | 运维核心需求           |

**设计理由：**

- **网关层独立**：认证、限流、输入清洗是安全边界，不应与业务逻辑耦合。工业系统中，安全组件必须独立于业务组件部署和升级。
- **L0 规则引擎前置**：电信运维 80% 的查询是模式化的（"查光纤 X 的衰耗"），用正则匹配 <500ms 即可响应，无需等待 LLM 3-5s 推理。
- **横切关注点独立**：审计、可观测、缓存、事件总线不属于任何单一层，而是贯穿所有层。

### 3.2 响应时间 SLA 分级

| 路径              | 触发条件                             | 目标延迟 | 实现手段                            |
| ----------------- | ------------------------------------ | -------- | ----------------------------------- |
| **Fast Path**     | L0 规则命中 + 单条查询               | **<1s**  | 规则引擎 + 直接 API 调用 + 模板输出 |
| **Normal Path**   | L0 未命中 + LLM 识别 + 单条/少量查询 | **<5s**  | LLM 意图识别 + API + LLM 表述       |
| **Heavy Path**    | 批量查询 / 报告生成 / 复杂分析       | **<15s** | Send 并发 + 流式输出                |
| **Degraded Path** | LLM 不可用 / 后端部分不可用          | **<2s**  | 规则兜底 + 缓存 + 模板              |

**设计理由：** 电信运维人员的耐心阈值约 3 秒。如果每次查询都要等 5-7 秒 LLM 推理，系统会被弃用。L0 规则引擎确保高频操作（查衰耗、看告警、查颜色）在 1 秒内响应。

  "现在有多少红色光纤"      ████████████          15%
  "光纤X的光功率"          ████████              10%
  "最近趋势怎么样"          ██████                8%
  ─────────────────────────────────────────────────
  以上合计（模式化查询）                          78%  ← 规则引擎可覆盖
  
  "帮我分析一下为什么最近红色光纤变多了"          7%
  "生成一份本周光纤健康报告"                      5%
  "1001和2003哪个衰耗更严重，原因是什么"          4%
  其他复杂/模糊查询                               6%
  ─────────────────────────────────────────────────
  以上合计（需要 LLM）                           22%  ← LLM 处理
```

**设计理由：** 用 3-5 秒 LLM 推理去处理"查光纤 1001 的衰耗"这种完全确定性的请求，是工程上的浪费。规则引擎以 <10ms 的成本覆盖 78% 的请求，LLM 只处理真正需要"理解"的 22%。

```

    PATTERN:
        regex: /(?:查询|查看|看看|帮我查).*?(\d+)\s*号?\s*(?:光纤|连纤|纤).*?(?:衰耗|损耗|衰减)/

    PATTERN:
        regex: /(\d+)\s*号?\s*(?:盘|板卡).*?(\d+)\s*号?\s*(?:口|端口).*?(?:告警|alarm)/
    EXTRACT:
        board_id = int(capture_group_1)
        port_id = int(capture_group_2)

        params = {board_id: board_id, port_id: port_id}

RULE "colored_stats" PRIORITY 90:
    PATTERN:
        regex: /(?:现在|当前|目前).*?(?:多少|几个).*?(红色|RED|红灯).*?(?:光纤|纤)/
    EXTRACT:

    EXECUTE:

        template = "当前红色光纤 {red_count} 条，黄色 {yellow_count} 条，活跃告警 {active_alarms} 条。"

RULE "trend_query" PRIORITY 80:

    EXTRACT:

    EXECUTE:

    RESPOND:

### 4.4 规则引擎与 LLM 的协作边界

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   用户输入                                                       │
│       │                                                          │
│       ▼                                                          │
│   ┌────────────┐     命中 (conf≥0.9)     ┌────────────────┐    │
│   │ Rule Engine │ ──────────────────────→ │ 直接执行+模板  │    │
│   │            │                         │ 输出 (<1s)     │    │
│   └─────┬──────┘                         └────────────────┘    │
│         │ 未命中 (conf<0.9)                                     │
│         ▼                                                        │
│   ┌────────────┐     识别成功            ┌────────────────┐    │
│   │ LLM Intent │ ──────────────────────→ │ 参数关卡 →     │    │
│   │ Translator │                         │ 执行 (<5s)     │    │
│   └─────┬──────┘                         └────────────────┘    │
│         │ 识别失败 / confidence < 0.7                            │
│         ▼                                                        │
│   ┌────────────┐                                                │
│   │ 追问用户    │  "您是想查询光纤衰耗，还是查看告警？"          │
│   └────────────┘                                                │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**设计理由：** 规则引擎不是"降级方案"，而是"主路径优化"。LLM 不是规则引擎的"上级"，而是规则引擎的"补充"。两者是平级协作关系。

## 第五部分：参数正确性保障体系（修订版）

### 5.1 从五层简化为"三层 + 两道断言"

v5.1 的五层防线存在 L2/L4 功能重叠。v6.0 重新划分职责：

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│  Layer 1: 提取层 (Extraction)                                    │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ 职责: 从用户输入中提取参数                                │    │
│  │ 执行者: 规则引擎(正则) 或 LLM(结构化输出)                │    │
│  │ 保障: Pydantic Schema 强制类型 (with_structured_output)  │    │
│  │ 输出: IntentResult (强类型)                              │    │
│  └─────────────────────────────────────────────────────────┘    │
│                          │                                       │
│                          ▼                                       │
│  Layer 2: 校验层 (Validation) ★ 核心防线                        │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ 职责: 业务规则校验 + 参数转换 + 缺失检测                 │    │
│  │ 执行者: Parameter Gate 节点 (确定性代码)                  │    │
│  │ 内容:                                                    │    │
│  │   • 必填检查 (按意图类型)                                │    │
│  │   • 范围检查 (int32: 1~2147483647)                      │    │
│  │   • 格式转换 ("FIB-1001"→1001, "红色"→"RED")           │    │
│  │   • 时间转换 ("最近一周"→ISO 8601)                      │    │
│  │   • 批量上限 (200/50)                                   │    │
│  │   • 歧义检测 (多个可能匹配→追问)                        │    │
│  │ 输出: validated_params 或 clarification_question         │    │
│  └─────────────────────────────────────────────────────────┘    │
│                          │                                       │
│                          ▼                                       │
│  Layer 3: 执行层 (Execution)                                     │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ 职责: 构造 HTTP 请求 + 解析响应                          │    │
│  │ 执行者: Tool 函数                                        │    │
│  │ 保障:                                                    │    │
│  │   • 断言 ①: assert isinstance(fiber_id, int)            │    │
│  │   • 断言 ②: assert 0 < fiber_id <= 2147483647          │    │
│  │   • 响应解析: Pydantic Model 反序列化                    │    │
│  │   • 错误映射: HTTP 400/404/500 → 用户友好提示           │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**设计理由：**

- Layer 1 和 Layer 2 的职责不再重叠：Layer 1 只管"提取"（是什么类型），Layer 2 管"校验"（是否合法、是否完整、如何转换）
- Layer 3 的两道断言是"最后防线"，成本极低（两行代码），但能防止 Layer 1/2 被绕过（如直接调用 Tool 的测试场景）
- 去掉了 v5.1 中 Tool 层的完整 Pydantic 校验（与 Layer 1 的 Schema 重复），减少约 40% 校验代码

### 5.3 追问机制设计

**设计理由：** 工业系统中，"猜错"比"多问一句"的代价大得多。查错光纤可能导致运维人员操作错误设备。因此，宁可多追问一次，不可猜错一次。

```
追问触发条件:
┌────────────────────────────────────────────────────────────────┐
│ 条件 1: 必填参数缺失                                           │
│   例: 用户说"查一下告警" → 缺 board_id, port_id                │
│   追问: "请提供单盘编号和端口号，例如：3号盘2号口"              │
│                                                                 │
│ 条件 2: 参数歧义                                               │
│   例: 用户说"1001的情况" → 1001 可能是 fiber_id 或 board_id    │
│   追问: "1001 是光纤编号还是单盘编号？"                        │
│                                                                 │
│ 条件 3: LLM 置信度 < 0.7                                       │
│   例: 用户说"那个东西怎么样了" → 无法确定意图                  │
│   追问: "您想查询什么？支持：光纤衰耗/告警/颜色统计/趋势..."   │
│                                                                 │
│ 条件 4: 批量超限                                               │
│   例: 用户说"查所有光纤" → 可能 >200 条                        │
│   追问: "当前共 350 条光纤，将查询前 200 条，是否继续？"       │
│                                                                 │
│ 条件 5: 危险操作确认（预留）                                    │
│   例: 未来若支持"清除告警"等操作                               │
│   追问: "确认要清除 3号盘2号口的所有告警？此操作不可撤销。"    │
└────────────────────────────────────────────────────────────────┘

追问约束:
  • 最多追问 2 轮，超过 2 轮 → 输出"无法理解，请使用以下格式：..."
  • 追问必须给出示例（降低用户认知负荷）
  • 追问不计入对话轮次（不消耗上下文窗口）
```

**设计理由：** Data Collector 内部不再使用 LLM（v5.1 中用 `create_react_agent` 让 LLM 决定调哪个 Tool）。v6.0 改为**确定性执行计划**——由 intent 类型直接映射到 Tool 调用序列。

原因：

- 规则引擎/Layer 2 已经确定了 intent 和参数，不需要 LLM 再"思考"调哪个 Tool
- 去掉 ReAct 循环减少 1-2 次 LLM 调用（节省 2-4s）
- 消除 LLM "选错 Tool" 的风险

### 6.2 Analysis Engine（规则判断 + LLM 表述）

```
┌─────────────────────────────────────────────────────────────────┐
│                  Analysis Engine                                  │
│                                                                  │
│  输入: StructuredData (来自 Data Collector)                      │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  Rule-Based Judgment (规则判断) ← 确定性，不经过 LLM     │   │
│  │                                                           │   │
│  │  • 衰耗判断: spanloss > threshold → "异常"               │   │
│  │  • 颜色判断: color == RED → "严重告警"                   │   │
│  │  • 趋势判断: 连续3天 red_count 上升 → "恶化趋势"        │   │
│  │  • 对比判断: fiber_A.spanloss > fiber_B.spanloss → 排序  │   │
│  │                                                           │   │
│  │  输出: judgment_result (结构化)                           │   │
│  │  {                                                        │   │
│  │    status: "abnormal",                                    │   │
│  │    severity: "warning",                                   │   │
│  │    key_findings: ["spanloss 3.2dB 接近阈值 5dB"],        │   │
│  │    recommendations: ["建议安排巡检"]                      │   │
│  │  }                                                        │   │
│  └──────────────────────────┬───────────────────────────────┘   │
│                             │                                    │
│                             ▼                                    │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  LLM Narrator (LLM 叙述器) ← 仅做语言组织               │   │
│  │                                                           │   │
│  │  输入: judgment_result + raw_data                         │   │
│  │  任务: 将结构化判断翻译为运维报告语言                     │   │
│  │  约束:                                                    │   │
│  │    • 不得修改任何数值                                     │   │
│  │    • 不得添加 judgment_result 中没有的判断                │   │
│  │    • 不得编造建议                                         │   │
│  │    • 仅做: 组织语言、排列段落、添加连接词                │   │
│  │                                                           │   │
│  │  [若 LLM 不可用] → 模板输出 (直接使用 judgment_result)   │   │
│  └──────────────────────────┬───────────────────────────────┘   │
│                             │                                    │
│                             ▼                                    │
│  输出: analysis_text (自然语言分析报告)                          │
└─────────────────────────────────────────────────────────────────┘
```

**设计理由：** v5.1 中 `analysis_expert` 让 LLM 同时做"判断"和"表述"，这违反了 P1 原则。v6.0 将两者分离：

- **判断**由规则引擎完成（确定性、可审计、可追溯）
- **表述**由 LLM 完成（自然、流畅、易读）

这样即使 LLM 产生幻觉，也只是"说得不好听"，不会"判断错误"。

### 6.3 批量处理引擎

│  │  Chunk Splitter (分块器)                                   │   │
│  │                                                           │   │
│  │  chunk_size = 50 (通用) 或 50 (告警，上限即50)           │   │
│  │  max_total = 200 (通用) 或 50 (告警)                     │   │
│  │                                                           │   │
│  │  200 条 → [chunk_0(50), chunk_1(50), chunk_2(50),        │   │
│  │            chunk_3(50)]                                    │   │
│  └──────────────────────────┬───────────────────────────────┘   │
│                             │                                    │
│                             ▼                                    │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  Send Dispatcher (LangGraph Send 并发)                     │   │
│  │                                                           │   │
│  │  Send("batch_worker", chunk_0)  ──┐                       │   │
│  │  Send("batch_worker", chunk_1)  ──┤  并发执行             │   │
│  │  Send("batch_worker", chunk_2)  ──┤  (受背压控制)         │   │
│  │  Send("batch_worker", chunk_3)  ──┘                       │   │
│  │                                                           │   │
│  │  每个 worker:                                             │   │
│  │    • 幂等键: {trace_id}_chunk_{idx}                      │   │
│  │    • 调用: batch_fiber_spanloss_query(chunk.fiber_ids)   │   │
│  │    • 输出: 仅统计摘要 (非原始数据)                        │   │
│  │      {count: 50, abnormal: 3, max_spanloss: 7.2,         │   │
│  │       abnormal_ids: [1023, 1067, 1089]}                   │   │
│  └──────────────────────────┬───────────────────────────────┘   │
│                             │                                    │
│                             ▼                                    │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  Aggregator (聚合器) ← 纯程序化，零 token                │   │
│  │                                                           │   │
│  │  • 合并 4 个 chunk 的统计摘要                             │   │
│  │  • 计算全局统计: total=200, abnormal=12, rate=6%         │   │
│  │  • 排序: 按 spanloss 降序取 Top-10                       │   │
│  │  • 仅将 Top-10 异常数据送入 LLM 分析                     │   │
│  └──────────────────────────┬───────────────────────────────┘   │
│                             │                                    │
│                             ▼                                    │
│  输出: batch_summary (结构化) + top_anomalies (≤10条)           │
└─────────────────────────────────────────────────────────────────┘
```

**设计理由：**

- 每个 worker 只返回**摘要**而非原始数据，避免 State 膨胀（200 条原始数据 → 4 个摘要 dict）
- 聚合器是纯程序化的（排序、计数、求最大值），不需要 LLM
- 只有 Top-10 异常数据进入 LLM 分析，控制 token 消耗

```

## 第十二部分：RAG 知识检索设计

### 12.1 架构（nomic-embed-text）

```
┌─────────────────────────────────────────────────────────────────┐
│                  RAG Pipeline                                     │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  入库流程 (离线)                                           │   │
│  │                                                           │   │
│  │  文档 → 分块(512 tokens) → 添加前缀                      │   │
│  │  "search_document: {content}"                             │   │
│  │       → OllamaEmbeddings(nomic-embed-text) → 768维向量   │   │
│  │       → ChromaDB 存储                                     │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  检索流程 (在线)                                           │   │
│  │                                                           │   │
│  │  查询 → 添加前缀 "search_query: {query}"                 │   │
│  │       → OllamaEmbeddings → 768维向量                     │   │
│  │       → ChromaDB 向量检索 (Top-5, threshold=0.5)         │   │
│  │       → BM25 关键词检索 (Top-5)                          │   │
│  │       → 混合排序 (Vector 0.6 + BM25 0.4)                │   │
│  │       → 取 Top-3 → 去前缀 → 返回                        │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  知识库内容 (首期 50+ 篇):                                       │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  • 光纤维护操作规程 (10篇)                                │   │
│  │  • 典型故障案例库 (20篇)                                  │   │
│  │  • 设备手册摘要 (按型号, 10篇)                            │   │
│  │  • 阈值标准文档 (按场景, 5篇)                             │   │
│  │  • 术语表 (1篇, 50+ 条)                                  │   │
│  │  • FAQ (10篇)                                            │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  使用场景:                                                       │
│  • Analysis Engine: 获取阈值标准 (规则判断的依据)               │
│  • Report Generator: 获取操作规程 (建议的来源)                  │
│  • Knowledge Assistant: 直接回答知识类问题                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**设计理由：** nomic-embed-text 通过 Ollama 部署，与 LLM 共享 GPU 资源，无需额外的 sentence-transformers 依赖（减少 ~2GB 镜像体积）。768 维向量在 ChromaDB 中检索性能优于 1024 维。前缀 `search_document:` / `search_query:` 是 nomic-embed-text 的官方推荐用法，可提升检索准确率约 5-10%。

### 14.2 HTTP Client 行为规格

```
┌─────────────────────────────────────────────────────────────────┐
│  HTTP Client 行为规格                                            │
│                                                                  │
│  认证:                                                           │
│  • 每个请求携带 Authorization: Bearer <jwt>                     │
│  • JWT 由网关层注入，Tool 层不感知认证逻辑                      │
│                                                                  │
│  超时分级:                                                       │
│  • 单条查询: 2s                                                  │
│  • 历史/趋势: 3s                                                 │
│  • 批量查询: 5s                                                  │
│  • 导出操作: 10s                                                 │
│                                                                  │
│  重试策略:                                                       │
│  • 5xx → 退避重试 (0.5s, 1.0s)，最多 2 次                      │
│  • 4xx → 不重试（客户端错误）                                   │
│  • 超时 → 退避重试 1 次                                         │
│                                                                  │
│  熔断器:                                                         │
│  • 连续 5 次失败 → OPEN (拒绝所有请求)                          │
│  • OPEN 持续 30s → HALF_OPEN (放行 1 个探测请求)               │
│  • 探测成功 → CLOSED                                            │
│  • 探测失败 → 继续 OPEN                                         │
│                                                                  │
│  背压控制:                                                       │
│  • 最大并发: 5                                                   │
│  • 请求间隔: ≥200ms                                              │
│  • 批量 Send: 受并发限制，4 个 chunk 串行执行                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 第十七部分：设计决策总结

### 17.1 每个关键决策的理由链

```
决策 1: L0 规则引擎前置
  因为: 电信运维 <2s 响应要求 + 78% 查询是模式化的
  所以: 用 <10ms 的正则匹配处理大部分请求
  代价: 需要维护 25-30 条规则
  收益: 80% 请求响应时间从 5s 降至 <1s

决策 2: LLM 只做翻译，不做判断
  因为: 7B 模型数学能力弱 + 电信计算可追溯性要求
  所以: 阈值判断、对比排序由规则引擎完成
  代价: 规则引擎需要覆盖所有判断逻辑
  收益: 消除 LLM 幻觉导致的误判风险

决策 3: 参数校验三层（非五层）
  因为: v5.1 五层中 L2/L4 功能重叠，增加维护成本
  所以: 提取(Schema) → 校验(Gate) → 断言(Tool) 三层
  代价: 无（安全性不降低）
  收益: 减少 40% 校验代码，降低维护复杂度

决策 4: Data Collector 不用 ReAct Agent
  因为: intent 已确定，不需要 LLM "思考"调哪个 Tool
  所以: intent → tool 序列的确定性映射
  代价: 灵活性降低（新增 intent 需要手动添加映射）
  收益: 减少 1-2 次 LLM 调用，节省 2-4s，消除选错 Tool 风险

决策 5: nomic-embed-text 替代 bge-large-zh
  因为: 用户要求本地 Ollama 部署 + 减少依赖
  所以: 通过 Ollama API 调用 embedding，无需 sentence-transformers
  代价: 768 维 vs 1024 维，检索精度略降；无配套 reranker
  收益: 镜像体积减少 ~2GB，部署简化，与 LLM 共享 GPU

决策 6: 全链路审计
  因为: 等保三级 + 电信运维合规要求
  所以: 每个请求记录完整审计日志，保存 ≥180 天
  代价: 每请求增加 ~5ms 写入开销 + 存储空间
  收益: 满足合规审计，支持故障复盘

决策 7: 本地缓存 + L4 离线降级
  因为: 电信机房存在网络分区场景
  所以: 每次 API 响应异步缓存，后端不可达时返回缓存
  代价: 数据可能不是最新（TTL 5min）
  收益: 网络中断时系统仍可用（降级但不宕机）

决策 8: WebSocket 事件驱动 + 主动巡检
  因为: 电信运维核心模式是"巡检+告警"而非"问答"
  所以: 订阅后端事件，CRITICAL 告警自动触发诊断
  代价: 增加常驻 WebSocket 连接 + 事件处理逻辑
  收益: 从"被动工具"升级为"主动助手"
```
