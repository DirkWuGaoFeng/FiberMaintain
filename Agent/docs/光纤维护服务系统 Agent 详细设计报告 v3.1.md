## 2 总体设计

### 2\.1 系统架构总览

系统基于 DeerFlow 2\.0 平台构建分层多智能体架构，自上而下分为 5 层：**交互层 → 编排层 → 能力层 → 连接层 → 后端服务层**。

```Plaintext
┌───────────────────────────────────────────────────────────────┐
│ 交互层：DeerFlow Web UI (:3000) + Vue3 统计面板 (:5173)       │
└─────────────────────────┬─────────────────────────────────────┘
                          │ HTTP/WebSocket
┌─────────────────────────▼─────────────────────────────────────┐
│ 编排层：Lead Agent + 全局中间件 + 任务调度器                    │
│         意图识别 / 任务分解 / 子智能体派遣 / 结果汇总            │
└─────────────────────────┬─────────────────────────────────────┘
                          │ task 工具调用
┌─────────────────────────▼─────────────────────────────────────┐
│ 能力层：4 类 Sub-Agent + 5 个 Markdown Skills                 │
│         topology-analyst / data-collector                     │
│         analysis-expert / report-generator                    │
└─────────────────────────┬─────────────────────────────────────┘
                          │ 工具调用
┌─────────────────────────▼─────────────────────────────────────┐
│ 连接层：MCP 连接器 + 18 个业务工具 + RAG引擎 + 记忆系统 + 沙箱  │
│         统一超时/重试/错误映射/审计/负载感知                    │
└─────────────────────────┬─────────────────────────────────────┘
                          │ REST API (:8080)
┌─────────────────────────▼─────────────────────────────────────┐
│ 后端服务层：C++ 微服务集群 + API Gateway + WebSocket (:8081)   │
└───────────────────────────────────────────────────────────────┘
```

## 3 Agent 层详细设计

### 3\.1 Lead Agent 详细设计

#### 3\.1\.1 基本配置

|配置项|值|
|---|---|
|角色|光纤运维智能助手主控|
|模型|qwen3\.6 primary|
|温度系数|0\.1（低随机性，保证稳定性）|
|最大迭代轮次|10|
|上下文窗口|8K|
|绑定工具|task（派遣子智能体）、memory\_query（会话记忆）|

#### 3\.1\.2 系统提示词核心约束

1. **身份定位**：你是专业的光纤运维智能分析助手，负责理解用户需求，调度专业子智能体完成任务，最终给出准确、结构化的结果。

2. **核心原则**：绝对不编造数据，所有业务数据必须通过子智能体从后端获取；绝对不做业务计算，所有状态判定以后端返回为准。

3. **任务调度**：复杂任务必须拆解为子任务，派遣对应领域的 Sub\-Agent 执行，禁止越权直接调用业务数据工具。

4. **输出规范**：结果必须结构化，关键数据以表格呈现；异常情况必须明确说明原因，不得含糊其辞。

5. **离线约束**：系统处于离线模式时，所有需要查询后端数据的请求，直接返回标准离线提示，不得尝试推理或编造数据。

6. **多轮对话**：主动复用上下文信息，支持用户指代省略；超出上下文范围时，主动询问补充。

#### 3\.1\.3 核心执行逻辑

1. **意图分类**：接收用户请求后，首先识别为 5 大类意图：

    - 拓扑查询类 → 派遣 topology\-analyst

    - 数据查询类 → 派遣 data\-collector

    - 分析诊断类 → 串行派遣 data\-collector → analysis\-expert

    - 报告导出类 → 串行派遣数据采集 → 分析 → report\-generator

    - 知识问答类 → 直接由 RAG 中间件注入知识后回答

2. **任务分解**：复杂请求拆解为有序子任务，明确每个子任务的输入、输出与依赖关系。

3. **结果汇总**：收集所有子智能体的返回结果，整理成统一格式的自然语言回复。

4. **异常处理**：子智能体执行失败时，自动重试 1 次；重试失败则向用户明确报错，说明失败原因。

### 3\.2 Sub\-Agent 详细设计

#### 3\.2\.1 topology\-analyst（拓扑分析师）

**定位**：纯拓扑数据查询代理，无任何业务判定逻辑。

|配置项|值|
|---|---|
|模型|qwen3\.6 fast|
|温度系数|0\.0|
|核心职责|连纤、单盘拓扑信息查询与格式化输出|
|禁止行为|场景识别、状态判定、业务计算|

**绑定工具**：

- `fiber_connection_query`

- `batch_fiber_connection_query`

- `board_query`

- `batch_board_query`

**执行逻辑**：

1. 接收 Lead Agent 传入的查询参数（fiber\_id 列表 / board\_id 列表）

2. 校验参数合法性，批量场景优先使用批量接口

3. 调用对应工具获取原始数据

4. 按固定 Markdown 表格格式整理返回

5. 不存在的条目明确标记，不编造信息

#### 3\.2\.2 data\-collector（数据采集师）

**定位**：全系统唯一的业务数据出口，所有原始性能、衰耗、告警、统计数据统一由本 Agent 提供。

|配置项|值|
|---|---|
|模型|qwen3\.6 fast|
|温度系数|0\.0|
|核心职责|业务数据查询、参数校验、批量请求组装|
|禁止行为|数据分析、结论生成、业务判定|

**绑定工具**：10 个业务数据类工具（详见第 4 章）

**执行逻辑**：

1. 接收查询参数与数据类型要求

2. 参数校验：批量数量不超过上限，ID 格式合法

3. 优先选择批量接口，减少请求次数

4. 调用 MCP 工具获取数据

5. 原始数据透传给下游，不做加工，附带请求状态说明

6. 部分失败场景，明确区分成功与失败条目

#### 3\.2\.3 analysis\-expert（分析专家）

**定位**：数据解读与分析专家，所有数据均来自上游，不直接接触后端接口。

|配置项|值|
|---|---|
|模型|qwen3\.6 primary|
|温度系数|0\.3|
|核心职责|数据解读、异常识别、纵向/横向对比、维护建议生成|
|数据来源|仅接受 data\-collector 传入的数据|

**绑定工具**：

- `memory_query`（长期记忆）

- `memory_save`（记忆写入）

- `sandbox_exec`（预留，默认禁用）

**执行逻辑**：

1. 接收上游传入的结构化数据与分析目标

2. 结合领域校验结果，标记异常数据项

3. 如需对比分析，调用长期记忆查询历史指标

4. 按业务规则进行分级（严重/预警/正常）

5. 生成分析结论与针对性维护建议

6. 输出结构化分析结果，包含数据概览、异常详情、建议清单

#### 3\.2\.4 report\-generator（报告生成师）

**定位**：报告输出与文件导出专员。

|配置项|值|
|---|---|
|模型|qwen3\.6 primary|
|温度系数|0\.2|
|核心职责|标准化报告生成、知识库引用、多格式导出|

**绑定工具**：

- `rag_query`（精准知识检索）

- `export_pdf`

- `export_excel`

- `export_csv`

**执行逻辑**：

1. 接收分析结论与原始数据

2. 如需补充规范依据，调用 `rag_query` 检索相关知识

3. 按标准报告模板生成完整 Markdown 报告

4. 根据用户需求调用导出工具，生成对应格式文件

5. 返回报告内容与下载链接

### 3\.3 Sub\-Agent 实例化与并发控制详细设计

#### 3\.3\.1 三级实例化模型

采用「**静态注册 \+ 按需实例化 \+ 批量单实例**」三级模型，兼顾灵活性与性能。

1. **注册层（静态常驻）**

    - 4 类 Sub\-Agent 以配置文件形式预先注册到 DeerFlow 平台

    - 注册内容：角色定义、系统提示词、绑定工具集、模型参数、超时配置

    - 仅存储元数据，无运行进程，零资源占用

2. **执行层（按需创建）**

    - Lead Agent 每次调用 `task` 工具时， DeerFlow 调度器动态创建对应类型的执行实例

    - 实例为独立上下文隔离环境，互不干扰

    - 任务执行完成（成功/失败/超时）后，实例立即销毁，释放资源

3. **批量层（单实例处理）**

    - 批量分析场景严格遵循「单实例批量处理」原则

    - 数据采集：创建 1 个 data\-collector 实例，调用批量接口一次性拉取全量数据

    - 分析解读：创建 1 个 analysis\-expert 实例，集中处理所有数据

    - 禁止为单条光纤单独创建 Sub\-Agent 实例

#### 3\.3\.2 并发控制实现

**实现机制**：全局信号量 \+ FIFO 等待队列

|参数|值|说明|
|---|---|---|
|全局并发数|5|同时运行的 Sub\-Agent 实例上限|
|队列策略|FIFO|超出并发数进入队列，按请求顺序执行|
|单实例超时|15s|单个 Sub\-Agent 最长执行时间|
|批量总超时|30s|批量场景整体超时阈值|
|队列最大长度|20|超出队列直接返回系统繁忙提示|

**后端负载联动限流**：

- MCP 连接器维护 1 分钟滑动窗口，统计 5xx 错误率

- 错误率 \> 10%：全局并发数自动降至 2

- 错误率 \< 3% 持续 1 分钟：恢复为 5

- 限流状态变更记录审计日志

### 4\.3 MCP 连接器详细设计

#### 4\.3\.1 架构定位

MCP 连接器是 Agent 层与后端服务之间的唯一交互通道，所有后端接口调用均通过 MCP Server 封装，统一处理认证、超时、重试、错误映射、审计、负载感知等横切逻辑。

#### 4\.3\.2 核心功能模块

1. **请求组装模块**：将工具参数转换为后端 HTTP 请求，添加 JWT 认证头

2. **超时控制模块**：单条接口 2s 超时，批量接口 5s 超时，严格对齐后端约定

3. **重试策略模块**：

    - 5xx 错误 \+ 超时：最多重试 2 次，退避间隔 500ms → 1000ms

    - 4xx 错误：不重试，直接返回业务错误

4. **错误映射模块**：将 HTTP 状态码与业务错误码转换为 Agent 可理解的错误类型

|HTTP 状态码|error\_code|映射错误类型|处理方式|
|---|---|---|---|
|400|INVALID\_ARGUMENT|参数错误|提示用户修正参数|
|400|BATCH\_LIMIT\_EXCEEDED|批量超限|自动拆分分批请求|
|404|NOT\_FOUND|资源不存在|标记为未找到|
|409|PORT\_OCCUPIED|业务校验失败|返回业务提示|
|5xx|\-|服务端错误|重试后失败报错|

5. **负载感知模块**：

    - 滑动窗口统计最近 1 分钟的请求错误率

    - 错误率阈值：10% 触发降载，3% 恢复

    - 通知 Agent 调度器调整全局并发数

6. **审计日志模块**：每次调用记录完整日志，包含 trace\_id、方法、路径、状态、耗时、入参摘要

## 5 中间件详细设计

全局共 4 个自定义中间件，分为**前置拦截**和**后置拦截**两类，执行顺序固定。

### 5\.1 执行顺序

```Plaintext
用户请求 → ModelDegradationMiddleware（前置）
        → RAGInjectionMiddleware（前置）
        → Agent 执行 + 工具调用
        → FiberDomainValidationMiddleware（工具后置，仅数据类）
        → AuditLogMiddleware（后置）
        → 返回用户
```

### 5\.2 ModelDegradationMiddleware（模型降级中间件）

**触发时机**：请求前置，Agent 推理前执行。

**核心逻辑**：

1. 检查当前系统健康状态：OLLAMA 服务状态、各模型可用性

2. 按优先级选择可用模型：primary → 简化 primary → fast → 规则兜底

3. 将选定模型配置注入当前会话上下文

4. 模型变更记录审计日志

**熔断器状态机**：

- **关闭状态**：正常运行，请求通过

- **打开状态**：连续 3 次失败触发熔断，持续 60s，期间直接使用下一级模型

- **半开状态**：冷却结束后放行 1 个探测请求，成功则关闭，失败则继续打开

**纯规则兜底触发逻辑**：

- 触发条件：所有 LLM 模型均不可用

- 生效范围：高频查询场景（单条性能查询、红色光纤列表、实时统计）

- 实现方式：直接调用后端 API，用预定义 Markdown 模板格式化输出，无需 LLM 推理

### 5\.3 RAGInjectionMiddleware（知识注入中间件）

**触发时机**：请求前置，Agent 推理前执行。

**核心逻辑**：

1. 对用户输入进行意图粗分类，匹配 6 大知识库类别

2. 对用户 query 进行改写优化，生成检索关键词

3. 调用 RAG 引擎执行混合检索 \+ Reranker 重排

4. 取 Top\-3 高相关片段，总 token 控制在 2000 以内

5. 将知识片段以系统提示形式注入对话上下文

6. 标记知识来源，便于后续溯源

**否定词过滤规则**：

- 包含“不要、不用、不需要、非”等否定词时，排除对应类别的知识库

- 例如“不用给我规范，直接说数据”，则不注入维护规范类知识

### 5\.4 FiberDomainValidationMiddleware（领域校验中间件）

**触发时机**：数据类工具调用后置，结果返回给 analysis\-expert 前执行。

**校验规则**：

|校验项|规则|异常处理|
|---|---|---|
|连纤合法性|src\_ne\_id \!= dst\_ne\_id|标记为异常连纤|
|OOP 范围|\-30 dBm ≤ value ≤ \+10 dBm|标记为光功率异常|
|IOP 范围|\-40 dBm ≤ value ≤ \+5 dBm|标记为光功率异常|
|衰耗范围|0 dB ≤ value ≤ 30 dB|标记为衰耗异常|

**处理方式**：

- 不丢弃异常数据，仅添加 `validation_warning` 标记字段

- 异常信息随数据一同传递给 analysis\-expert，由其在结论中明确标注

- 校验失败记录审计日志

### 5\.4 AuditLogMiddleware（审计日志中间件）

**触发时机**：全链路后置，响应返回用户前执行。

**记录内容**（JSON Lines 格式）：

```JSON
{
  "trace_id": "uuid-string",
  "timestamp": "ISO8601",
  "session_id": "session-id",
  "stage": "tool_call / agent_call / request",
  "name": "工具/Agent名称",
  "status": "success / failed / degraded",
  "duration_ms": 123,
  "input_summary": "入参摘要",
  "error_code": "错误码（可选）",
  "error_msg": "错误信息（可选）"
}
```

**存储策略**：

- 审计日志：保留 90 天，按天切割文件

- 运行日志：保留 30 天，按级别输出

## 6 Markdown Skills 详细设计

Skills 是固化的标准化业务流程，通过 Markdown 定义执行步骤，强制 Agent 按流程执行，降低自由发挥的不确定性。

### 6\.1 fiber\_spanloss\_analysis（衰耗分析技能）

**适用场景**：单条/批量光纤衰耗状态分析
**输入**：fiber\_id 列表
**输出**：标准化衰耗分析表格 \+ 结论

**执行步骤**：

1. **参数校验**：确认光纤 ID 列表非空，批量数量不超过 200

2. **数据采集**：派遣 data\-collector 调用 `batch_fiber_spanloss_query` \+ `batch_fiber_performance_query` 获取全量数据

3. **领域校验**：自动触发领域校验中间件，标记异常数据

4. **知识注入**：自动注入《光纤衰耗阈值表》作为判定参考

5. **分析解读**：派遣 analysis\-expert 基于后端数据与阈值标准，生成状态判定与异常说明

6. **结果输出**：按标准表格输出，包含光纤 ID、衰耗值、光功率、状态、异常说明

### 6\.2 fiber\_color\_diagnosis（颜色诊断技能）

**适用场景**：异常光纤诊断与处理建议
**输入**：颜色筛选条件（RED/YELLOW/全部）
**输出**：异常光纤列表 \+ 场景说明 \+ 处理建议

**执行步骤**：

1. **数据采集**：派遣 data\-collector 调用 `colored_fibers_query` / `all_colored_fibers_query` 获取异常列表

2. **补充信息**：按需补充对应光纤的告警、性能数据

3. **场景展示**：直接展示后端返回的 `scene_type` 和 `scenario_case`，**不做任何场景判定**

4. **优先级排序**：按红色优先、同色按衰耗从大到小排序

5. **知识匹配**：注入对应告警处理指南与故障案例

6. **建议生成**：生成分级处理建议，标注 P0\~P3 优先级

### 6\.3 batch\_fiber\_analysis（批量分析技能）

**适用场景**：指定光纤列表的批量健康分析
**输入**：fiber\_id 列表
**输出**：批量分析汇总报告

**执行步骤**：

1. **批量拉取**：派遣 data\-collector 调用批量接口，一次性获取所有光纤的拓扑、性能、衰耗、告警数据

2. **集中解读**：派遣 1 个 analysis\-expert 实例批量处理所有数据，禁止逐条创建实例

3. **分级分类**：按健康状态分为正常、黄色预警、红色异常三类

4. **共性归纳**：归纳同网元、同盘位的共性异常问题

5. **报告生成**：生成汇总报告，包含统计概览、异常清单、优先处理建议

6. **结果统计**：明确标注成功条数、失败条数及失败原因

### 6\.4 fiber\_trend\_analysis（趋势分析技能）

**适用场景**：一段时间内的异常光纤数量趋势研判
**输入**：时间范围（start\_time, end\_time）
**输出**：趋势分析结论

**执行步骤**：

1. **数据获取**：派遣 data\-collector 调用 `fiber_trend_query` 获取趋势点数据

2. **特征识别**：派遣 analysis\-expert 识别异常突增、持续劣化、周期波动等特征

3. **历史对比**：调用长期记忆，与上一周期做同比/环比对比

4. **结论生成**：生成趋势判断、风险预警与维护建议

### 6\.5 ne\_health\_check（网元巡检技能）

**适用场景**：指定网元的全量健康巡检
**输入**：ne\_id
**输出**：网元巡检报告

**执行步骤**：

1. **拓扑获取**：派遣 topology\-analyst 获取网元下所有单盘与关联连纤列表

2. **批量采集**：派遣 data\-collector 批量拉取所有连纤的性能、衰耗、告警、颜色数据

3. **逐条检查**：派遣 analysis\-expert 逐条检查健康状态

4. **评分计算**：按异常比例计算网元健康度评分

5. **报告输出**：生成完整巡检报告，包含问题清单与整改建议

## 7 RAG 知识库详细设计

### 7\.1 技术架构

```Plaintext
文档上传 → 文档解析 → 文本分块 → 向量化 → 存入 ChromaDB
                                                      ↓
用户查询 → 查询改写 → 混合检索（向量+BM25） → Reranker 重排 → Top-3 注入上下文
```

### 7\.2 核心配置

|配置项|值|
|---|---|
|向量数据库|ChromaDB 本地持久化|
|Embedding 模型|BAAI/bge\-large\-zh\-v1\.5|
|分块大小|512 tokens|
|分块重叠|50 tokens|
|检索策略|混合检索：向量 0\.6 权重 \+ BM25 0\.4 权重|
|重排模型|bge\-reranker\-large|
|返回数量|Top\-3|
|相似度阈值|0\.6（低于阈值不返回）|

### 7\.3 知识库集合设计

按业务类别分为 6 个 Collection，便于按意图精准检索：

|Collection 名称|文档数量|内容类别|
|---|---|---|
|device\_manual|3|设备技术手册|
|maintenance\_spec|3|维护操作规范|
|alarm\_guide|3|告警处理指南|
|fault\_case|3|历史故障案例|
|threshold\_std|2|衰耗阈值标准|
|ne\_config|2|网元配置规范|

### 7\.4 Mock 初始化方案

**初始化脚本流程**：

1. 读取 `mock_docs/` 目录下 6 个子目录的 16 篇 Markdown 文档

2. 按文档对应 Collection 分类

3. 对每篇文档执行：解析 → 分块 → 向量化 → 入库

4. 输出初始化统计：成功文档数、总分块数、耗时

5. 生成初始化校验报告，验证检索可用性

**Mock 文档规范要求**：

- 统一 Markdown 格式，标题层级清晰

- 关键指标、阈值使用表格呈现，便于检索命中

- 每篇文档包含明确的业务场景标签

- 无歧义表述，避免口语化内容

## 8 记忆系统详细设计

### 8\.1 整体架构

分为**短期会话记忆**和**长期指标记忆**两层，均基于 SQLite 存储。

```Plaintext
用户对话 → 短期记忆（会话级，50条） → 对话摘要压缩
                ↓
          关键指标提取 → 长期记忆（持久化，指标快照）
```

### 8\.2 短期记忆设计

**存储位置**：SQLite 内存模式（会话内）\+ 持久化会话表（历史会话）
**生命周期**：当前会话保留 50 条消息；历史会话保留 30 天

**核心表结构**：

```SQL
-- 会话表
CREATE TABLE sessions (
    session_id TEXT PRIMARY KEY,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT DEFAULT CURRENT_TIMESTAMP,
    message_count INTEGER DEFAULT 0,
    summary TEXT
);

-- 消息表
CREATE TABLE messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    role TEXT NOT NULL, -- user / assistant
    content TEXT NOT NULL,
    timestamp TEXT DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(session_id)
);
CREATE INDEX idx_msg_session ON messages(session_id, timestamp DESC);
```

**摘要压缩机制**：

- 触发条件：单会话消息数 \> 30 条

- 执行方式：调用 LLM 将最早 10 条对话压缩为一段摘要

- 替换规则：原消息移出上下文，替换为摘要，控制总 token 量

### 8\.3 长期记忆设计

**定位**：仅存储关键指标快照，用于对比分析，不存储完整分析结果。
**存储位置**：SQLite 持久化文件，预留 PostgreSQL 迁移接口

**核心表结构**：

```SQL
CREATE TABLE long_term_memory (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    fiber_id INTEGER NOT NULL,
    record_time TEXT NOT NULL, -- ISO8601 指标时间
    spanloss REAL,
    color TEXT, -- GREEN / RED / YELLOW
    summary TEXT, -- 一句话状态摘要
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

-- 联合索引，加速按光纤+时间查询
CREATE INDEX idx_fiber_time ON long_term_memory(fiber_id, record_time DESC);
```

**写入逻辑**：

- 触发时机：每次分析完成后，由 analysis\-expert 调用 `memory_save` 写入

- 写入方式：异步队列写入，不阻塞主响应流程

- 去重规则：同一 fiber\_id 同一小时内仅保留 1 条记录，避免数据冗余

**查询逻辑**：

- 支持按 fiber\_id \+ 时间范围查询历史指标

- 默认返回最近 10 条记录，用于纵向对比

### 9\.4 启用约束

1. 必须经过业务评估，确认后端无法支持该计算逻辑

2. 仅用于非核心、辅助性的扩展计算

## 11 错误处理与容错设计

### 11\.1 错误分级

|错误等级|定义|示例|处理方式|
|---|---|---|---|
|L1 参数错误|用户输入不合法|ID 格式错误、批量超限|提示修正，自动补全|
|L2 业务错误|业务校验不通过|光纤不存在、端口已占用|明确告知原因，不重试|
|L3 服务错误|后端服务异常|5xx、超时|自动重试，失败降级|
|L4 系统错误|核心组件故障|OLLAMA 宕机、数据库不可用|触发兜底机制，告警|

### 11\.2 四级兜底机制

|层级|触发条件|表现形式|用户感知|
|---|---|---|---|
|L1 正常|所有服务正常|完整智能分析 \+ 自然语言交互|无感知|
|L2 模型降级|主模型超时/失败|自动切换轻量模型，效果略降|基本无感知，响应可能稍快|
|L3 规则兜底|所有 LLM 不可用|高频查询用固定模板输出结构化数据|能查数据，无智能分析与自然语言|
|L4 纯知识模式|后端服务不可用|仅支持知识库问答，数据查询明确拒绝|感知明显，有明确离线提示|

### 11\.3 熔断器设计

**针对对象**：每个模型规格、每个后端接口分别设置熔断器
**状态流转**：

1. **关闭（Closed）**：正常状态，所有请求通过

2. **打开（Open）**：连续失败达到阈值（3 次），熔断 60s，请求直接走降级逻辑

3. **半开（Half\-Open）**：熔断冷却后，放行 1 个探测请求

    - 成功 → 回到关闭状态

    - 失败 → 回到打开状态，重新计时

## 14 测试策略

### 14\.1 单元测试

- **覆盖范围**：所有工具函数、中间件逻辑、数据处理函数

- **测试内容**：参数校验、正常流程、异常分支、边界条件

- **通过率要求**：核心模块 100% 通过

### 14\.2 集成测试

- **覆盖范围**：Agent 与工具、Agent 与中间件、Agent 与记忆/RAG 的集成

- **测试内容**：工具调用链路、中间件拦截效果、记忆读写、知识库检索

- **重点验证**：权限隔离、错误传递、数据一致性

### 14\.3 端到端测试

- **测试集**：20\~30 条标准用例，覆盖 5 大类核心场景

- **评估方式**：LLM\-as\-Judge \+ 规则校验

- **校验维度**：

    1. 准确性：数据与后端一致，无编造

    2. 格式规范性：输出结构符合要求

    3. 流程正确性：按 Skill 流程执行，工具调用顺序正确

    4. 幻觉率：无事实性错误

### 14\.4 专项测试

1. **降级专项**：模拟模型故障、后端故障，验证降级机制生效

2. **并发专项**：压测最大并发数，验证限流与队列机制

3. **批量专项**：200 条批量查询，验证性能与正确性
